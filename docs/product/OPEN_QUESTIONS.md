## Vines Production decisions

- **Vines Grow Cube disposition correction: replace-mode deferred.** `VINES-OPS-002` implements void-only correction (`production_disposition_service.correct_grow_cube_disposition`) for a Vines `grow_bag` disposition REDUCTION -- a pure reversal that restores every one of the target event's own named Grow Cube(s) to disposal eligibility, delegating unmodified to the already carrier-agnostic `correct_disposition`. REPLACE-mode correction (voiding an original loss and simultaneously recording a corrected replacement REDUCTION) is NOT exposed for Vines: `correct_disposition`'s existing REPLACE shape carries only a bare `plant_loss_count`, with no field for which specific Grow Cube(s) the replacement names, and fabricating that identity (e.g. reusing the original event's own Grow Cubes) would be an invented fact, not a derived one, when the correction's whole point may be that the ORIGINAL identification was wrong. Extending `ProductionDispositionEvent`'s REPLACE shape to carry an explicit corrected Grow Cube set is left for a follow-up ticket rather than rushed here (per the ticket's own instruction: "if extending correction materially complicates this ticket, STOP ONLY that subpart"). Void-then-re-record (two separate, already-supported commands) is the current operator path for a full "I identified the wrong plant" correction.

## Crop Observations operator UI decisions

- **No farm/tenant-wide observation feed.** `AGRONOMY-OPS-001` built the Observations workspace (`/farms/{farmId}/observations`) strictly against the existing backend surface: `GET .../crop-batches/{batch_id}/observations` is per-Batch only, with no farm- or tenant-wide "recent observations across every batch" read. The ticket's own compact mockup showed a cross-batch log, but the ticket also scoped the allowed backend change to "one small read endpoint... for usable UI target selection" — a farm-wide observation feed is a materially larger read (aggregation, pagination, filtering) past that allowance, not the target-selection gap it was meant for. The shipped UI instead requires selecting a Batch first, then shows that Batch's own observation log — operationally reasonable (a grower reviewing "this batch's" history), but not the cross-batch feed literally pictured. Adding a real farm-wide feed is a separate, larger backend ticket.
- **No "Recorded by" display name anywhere in this app yet.** `ObservationEventRead.actor_user_id` is a raw UUID with no resolution to a display name in any existing frontend code path — every other operational history panel already built (Plant Loss History, Vines Loss History, Harvest History) likewise omits "recorded by" from its UI for the same reason: surfacing the raw UUID would violate the "no UUIDs in normal UI" rule (`CLAUDE.md`), and there is no `/users` list or actor-name-resolution endpoint to call instead. The Observation History table omits this column, consistent with existing precedent, rather than inventing a lookup. A general actor-name-resolution capability (e.g. a `GET /users?ids=` batch lookup, or embedding a display name summary directly in relevant `*Read` schemas) would benefit every history view in the app, not just Observations, and is left as a cross-cutting follow-up rather than a one-off fix here.
- **Carrier target location resolution covers direct Location occupancy only.** The new `GET .../crop-batches/{batch_id}/observation-targets` read (added by this ticket) resolves a carrier's current location only when its active `Occupancy` targets a `Location` directly; a carrier occupying an `asset_position` (e.g. a Nursery Tray resting on a specific Trolley level) shows no location in the target picker rather than walking through the asset to its own location. This mirrors `production_disposition_service.list_active_production_plates`'s own established scope (same limitation, same precedent) rather than introducing new asset-position-aware location-resolution logic; the UI degrades gracefully (shows the carrier code with no location) rather than fabricating one.

## Planning decisions

- **No yield/duration/density assumptions existed to reuse.** Before building `PLANNING-OPS-001`, the repo was checked for any already-configured crop cycle-duration, expected-yield, plant-density, or germination-rate data (`Crop`, `Variety`, `Workflow`, `WorkflowStage` models/migrations) — none exists. Per the ticket's own explicit instruction, none was invented: the planner enters `required_quantity` (demand), `planned_quantity` (seed/plant count), and `expected_coverage_quantity` (the planner's own honest estimate of what that sowing will cover) all by hand; CMP performs no yield derivation. Automatic optimization is future work, not scoped here.
- **`expected_coverage_uom_id` is forced to exactly equal the parent Production Requirement's own `quantity_uom_id`.** A plan line's coverage and the requirement's demand are summed directly with no conversion step. The alternative — allowing a different UOM and silently converting via `uom_conversion_service` — was rejected: `EA`/`SEED`↔mass conversion has no real-world factor to convert with (a seed count cannot be converted to a harvested kg estimate without exactly the yield assumption the ticket forbids inventing), and even a valid mass↔mass conversion would quietly blur "the planner's own coverage estimate" into "a system-computed estimate," which is a bigger judgment call than this ticket's scope. Locking the UOM keeps every coverage number an honest, unconverted, planner-entered figure.
- **Production Requirement `status` has no `reopen` command.** OPEN → CLOSED and (from OPEN or CLOSED) → CANCELLED are implemented; the ticket's own status vocabulary section describes only these three states with CLOSED/CANCELLED read as effectively terminal for planning purposes, and no reopen flow was described in the compact UX. If a planner needs to resume planning against a closed requirement, the current path is creating a new Production Requirement. Left as a genuine gap rather than invented.
- **Update/close/cancel commands are idempotent by final state, not by full command-replay dedup.** Mirrors `LocationUpdate`/`LocationDeactivate`/`LocationReactivate`'s own established per-command `<verb>_client_command_id`/`<verb>_request_fingerprint` column-pair pattern exactly (see `docs/domain` — UX-IA-001). A second, different `client_command_id` cancelling an already-cancelled row is treated as a harmless no-op (same target state) rather than raising a conflict, which is a deliberate, existing precedent in this codebase (`location_service.deactivate_location`), not a Planning-specific shortcut.
- **Seeding Program Line `crop_id` must exactly equal its parent Production Requirement's `crop_id`; `variety_id` is independent (optional, unchecked against the requirement's own variety).** A plan line's whole purpose is fulfilling ITS requirement's demand, so a crop mismatch is rejected outright as nonsensical; variety substitution (planting a different but acceptable variety of the same crop to meet the same demand) is a real planning scenario the ticket's own example data doesn't rule out, so it is allowed.
