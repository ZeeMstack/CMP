# Carrier Release and Transplantation Transformation Model

Full detail: `CMP_MASTER_SPEC.md` §2, §8; `CLAUDE.md` rules 1, 3, 4, 5, 6, 7, 8, 10, 12. This document summarizes the approved model as implemented in CMP-011; it does not restate the spec.

## Scope

CMP-011 is the first *transformation* (rule 6): a controlled, single-step move of a crop batch's identity off its seed-tray carriers (assigned by CMP-009 sowing) and onto new destination carriers, with exact integer plant-count lineage. It amends the CMP-009 `batch_carrier_assignment` shape — adding a typed closing command and a second typed opener — rather than building a parallel model, exactly as CMP-009's own model doc anticipated. Out of scope: repeated/chained transplantation, batch split/merge, new batch creation, stage progression (automatic or otherwise), carrier movement or occupancy changes, capacity configuration, inventory deduction, observations, quality scoring, harvest, packing, QR/labels, frontend, RLS, role-specific authorization, and releasing a transplant-created assignment (only sowing-origin assignments are releasable in CMP-011).

## Assignment origin and release

A `batch_carrier_assignment` now has exactly one opener — `opening_sowing_event_id` (CMP-009) or `opening_transplant_event_id` (CMP-011), enforced by a CHECK constraint — and an optional release, `released_by_transplant_event_id`, present if and only if `released_effective_time` is present. Only a sowing-origin assignment may ever be released (`CHECK (released_by_transplant_event_id IS NULL OR opening_sowing_event_id IS NOT NULL)`); a transplant-created assignment could not itself be transplanted again in CMP-011. **Superseded by NURSERY-OPS-005A** (see addendum below): a transplant-created assignment on a `nursery_cultivation_plate`-typed Carrier is now itself an eligible Transplant source, and its release CHECK constraint was widened accordingly. A transplant-created assignment on any OTHER Carrier type (in particular `production_cultivation_plate`) remains ineligible as a source — this section's original restriction still holds for those. `required_carrier_type_id` on a `workflow_stage` identifies the carrier type a stage-specific operation may *newly assign* — for seeding, sown carriers; for transplanting, destination carriers — it does not retroactively require carriers already active when the batch entered that stage to match. This is why a batch's original seed-tray assignments remain active and untouched while the batch sits in a transplanting-category stage; only a transplant command's destination carriers are checked against it.

## Transplant events, source lines, destination lines, allocations

One `transplant_event` is one command, tied by trigger to the batch's exact active stage run, which must be `transplanting`-category with a configured `required_carrier_type_id`. It carries one or more `transplant_source_lines` (one active, sowing-origin assignment each — `UNIQUE(source_batch_carrier_assignment_id)` globally, so a given assignment can be the source of at most one transplant, ever) and one or more `transplant_destination_lines` (one carrier each, freshly assigned — `UNIQUE(destination_batch_carrier_assignment_id)` globally). `transplant_allocations` are the many-to-many bridge between them, each an integer plant count moving from one source line to one destination line (`UNIQUE(source_line_id, destination_line_id)`).

**Fully-discarded source policy**: a source line may have zero allocations only when `discarded_plant_count == source_plant_count` — a total-loss tray. Every other source line requires at least one allocation; every destination line always requires at least one (`assigned_plant_count > 0` forces it). An event whose sources are all fully discarded is impossible in practice since the schema also requires at least one destination line and one allocation.

## Reconciliation

Per source line: `discarded_plant_count + sum(its allocations) == source_plant_count`. Per destination line: `sum(its allocations) == assigned_plant_count`. Per event (rule 8): `total_source_plant_count == total_destination_plant_count + total_discarded_plant_count`. No difference is ever hidden — a mismatch anywhere rejects the whole command.

Reconciliation is validated twice: in-memory before any write, and again by a single database function (`enforce_transplant_reconciliation`) attached to **six** `DEFERRABLE INITIALLY DEFERRED` constraint triggers — `AFTER INSERT` on `transplant_events`, `transplant_source_lines`, `transplant_destination_lines`, and `transplant_allocations`; `AFTER INSERT` on `batch_carrier_assignments` when a transplant-origin opener is set; `AFTER UPDATE` on `batch_carrier_assignments` when a release transitions from unset to set. All six resolve to the same affected event and re-validate its *complete* state at real transaction commit, not at each individual insert — this is what defends against a later, separate transaction inserting an extra row (e.g. a stray allocation) against an already-committed event via direct SQL.

## Locking and idempotency

Locking order: the crop batch row, its active stage run, then all source and destination carriers together in one sorted-UUID set (not two separately ordered groups, to avoid deadlocking against a concurrent command touching an overlapping carrier set from the other side), then the source assignments in sorted-UUID order. `UNIQUE(tenant_id, client_command_id)` on `transplant_events`; the fingerprint covers tenant, farm, actor, batch, UTC effective time, normalized note, and the source/destination/allocation lines sorted by their stable domain identifiers (`source_assignment_id`, `destination_carrier_id`) — it excludes the active stage-run id and current assignment/carrier state, so a retry still returns the original event after the batch has progressed or carriers have changed state.

## Database protection

Composite foreign keys (`(tenant_id, farm_id, batch_id, id)`-style, matching CMP-008/009/010) prove tenant/farm/batch consistency structurally for all four new tables, including 4-column FKs from `transplant_allocations` to its source/destination lines that structurally prove same-event membership. The CMP-009 `batch_carrier_assignments` insert-integrity and no-update triggers/functions are left completely untouched in the database; only their trigger *attachments* were dropped and replaced with new CMP-011-named triggers/functions (`enforce_batch_carrier_assignment_origin_insert_integrity`, branching on whichever opener is set; `enforce_batch_carrier_assignment_closure_only`, allowing exactly the release fields to move once). This means a downgrade restores CMP-009's original behavior by simply re-attaching a trigger to the original function — zero risk of textual divergence. All four new tables are append-only/no-delete (`reject_append_only_mutation`, shared with CMP-008/009/010).

## Downgrade guard

Downgrading past CMP-011 is destructive to production history by nature (it would drop the assignment-origin/release columns and the four transplant tables). The migration's `downgrade()` therefore queries, before any DDL, for the existence of any `transplant_events` row, any `batch_carrier_assignment` with a transplant-origin opener or release, or any `workflow_stage` with `stage_category = 'transplanting'`; if any exist, it raises `RuntimeError` and aborts with zero schema change. Only on a database that has never run a transplant and never configured a transplanting-category stage does downgrade proceed, fully restoring the exact CMP-009 shape.

## Deferred

Repeated/chained transplantation, releasing a transplant-created assignment, new batch creation, stage auto-progression, quality-hold-blocks-transplantation (holds remain a stage-progression lock only), inventory, harvest, packing, QR identities, labels, RLS, role-specific authorization beyond `transplant.manage`/`transplant.read`.

Batch split/merge is implemented — see `docs/domain/BATCH_DERIVATION_MODEL.md` (CMP-012). It widens the assignment-origin CHECK to a third opener (`opening_batch_derivation_event_id`) and, for derivation-release only, drops the sowing-origin-only restriction described above under Assignment origin and release; transplant-release itself is unchanged.

## NURSERY-OPS-004A addendum: SeedlingEntry-anchored source authority

The reconciliation model above (source lines, destination lines, allocations, the six deferred triggers) is unchanged, but source authority itself was superseded before 004B: `source_plant_count`/`source_available_before` is no longer read from the original sowing quantity. It is derived entirely from the source `SeedlingEntry` (NURSERY-OPS-003A) plus `SeedlingDispositionEvent`s and `SeedlingSourceCheckpoint`s (NURSERY-OPS-003B/004A) — never bounded by `sown_site_count`/`seed_count`. A source assignment with no `SeedlingEntry` at all has no authoritative quantity to derive and is rejected (`SourceAssignmentHasNoSeedlingEntryError`). Each transplant inserts exactly one `SeedlingSourceCheckpoint` per source line, chained to the prior checkpoint for that Tray, recording `remainder_after`; a later transplant's `effective_time` must fall strictly after the latest checkpoint's own `effective_time` (or, if no checkpoint exists yet, at or after the `SeedlingEntry`'s own `effective_time`). The locking order given above is extended accordingly: after locking source assignments, each source's `SeedlingEntry` row is also locked (deterministic id order), before resolving the availability anchor.

## NURSERY-OPS-004B.1 addendum: destination biological capacity and composite physical placement

**Destination capacity.** `TransplantDestinationLine.assigned_plant_count` must not exceed the destination Carrier's `CarrierSpecification.biological_position_count`, enforced inside `_record_transplant_core` itself, under the same Carrier row lock the pre-existing `DestinationCarrierAlreadyAssignedError` check already holds — no new locking. The rule is symmetric to CARRIER-CONFIG-001B's Sowing-capacity rule but does not need a third quantity the way Sowing does: `assigned_plant_count` is a direct 1:1 physical-position count (one transplanted seedling occupies exactly one Plate cell), unlike Sowing's `seed_count` (which may be many-per-position and is therefore never compared against capacity). Generic rule: if the destination CarrierType requires a specification, one must exist with a positive `biological_position_count` or the command is rejected (`TransplantValidationError`); if a capacity is known regardless of whether the type requires one, it is enforced (`TransplantCapacityExceededError`); if no capacity is known, none is invented. Deactivating a `CarrierSpecification` never revokes Transplant eligibility for a Carrier that already references it — only new Carrier registrations are blocked (see `docs/domain/ASSET_CARRIER_MODEL.md`'s specification lifecycle). Backstopped at the DB layer by `enforce_transplant_destination_capacity`, a `DEFERRABLE INITIALLY DEFERRED` `AFTER INSERT` constraint trigger on `transplant_destination_lines` (migration `b7e2f4a9c1d6`), following the exact same architecture as this document's own `enforce_transplant_reconciliation` — unreachable via the normal application path, pure defense-in-depth against a direct-SQL bypass of the service layer.

**Composite physical placement.** `intersalads_transplant_service.record_intersalads_transplant` composes `_record_transplant_core` with `movement_service._execute_movement_core` (one Movement per destination Plate, onto its selected InterSalads Table) under one caller-owned transaction — the first real production use of the composability both cores' own docstrings anticipated. Movement gains zero Transplant/biology awareness from this composition; every check specific to the composite lives in `intersalads_transplant_service` alone. Execution order is dictated by both cores' own documented constraint (a caller composing them must run `_record_transplant_core` first, before any write it cannot afford to lose to that core's own internal IntegrityError-triggered rollback), not a style choice. Each destination Plate's Movement gets its own deterministically-derived `client_command_id` (outer command id + destination Carrier id, mirroring `seedling_entry_service`'s established single-movement derivation, extended for N destinations) — reusing the outer id directly would violate Movement's own per-command uniqueness after the first destination. On an exact-fingerprint replay of the outer command, the composite does not re-invoke the movement cores (safe but wasteful); it re-derives the expected Movement ids, loads them, and verifies each matches the requested destination Carrier/Location, raising `IntersaladsTransplantReplayStateConflictError` on any mismatch (this also covers a same-command-id resubmission with a different destination Location — a fact the generic Transplant fingerprint has no way to cover, since it has no concept of location at all). No compensating deletes anywhere: any failure, in either core, rolls back the entire transaction.

Physical placement requires one new `occupancy_compatibility_rules` row (`nursery_cultivation_plate` → `intersalads_table`, migration `b7e2f4a9c1d6`) — CARRIER-CONFIG-001B's own carrier-type migration deliberately left this open for this ticket. Table Carrier-count capacity (`Location.capacity`, DOMAIN-FARM-002) is reused entirely unmodified; it is a distinct concept from Plate biological capacity above and neither this ticket nor Movement conflates them.

Gated by `Permission.TRANSPLANT_MANAGE` alone, not `MOVEMENT_MANAGE` in addition — the physical placement is an inseparable side effect of the biological Transplant, the dominant and harder-to-reverse operation. Audit is the two existing underlying events, unmodified and unsuppressed (`crop_batch.transplanted` once, `movement.executed` once per destination) — no synthetic composite audit event.

## TRANSPLANT-CORRECTION-001 addendum: correction (reversal / replacement)

Correction/void for a wrong biological Transplant is implemented as an immutable REVERSAL, plus an optional REPLACEMENT, of a directly-targeted `TransplantEvent` — never a mutation of the original. `TransplantEvent.event_kind` (`RECORD`/`REVERSAL`/`REPLACEMENT`) extends the pre-existing RECORD shape; a REVERSAL names its target via `reverses_transplant_event_id` and carries a required, non-empty `correction_reason`; a REPLACEMENT names its target via `corrects_transplant_event_id`. Both point at the SAME target directly, never at each other, mirroring the Seedling Disposition RECORD/REVERSAL/replacement precedent (`NURSERY-OPS-003B`) exactly — so a REPLACEMENT can itself later become the target of a further correction with zero special-casing. A REVERSAL may never itself be corrected; only `RECORD`/`REPLACEMENT` targets are eligible. `UNIQUE(reverses_transplant_event_id)`/`UNIQUE(corrects_transplant_event_id)` (partial, `WHERE NOT NULL`) enforce at most one of each per target; a `DEFERRABLE INITIALLY DEFERRED` constraint trigger proves at commit that any REPLACEMENT is paired with a REVERSAL of the same target — a pure void (REVERSAL only) remains valid.

**Effective time vs. recorded time.** The caller never supplies a correction effective time. For target `TransplantEvent.effective_time = T`, both the REVERSAL and (if present) the REPLACEMENT are server-forced to `effective_time = T` — their own `recorded_time` (server default, unchanged column) is the true "when was this correction actually entered" fact. This is intentional: the correction records what biologically happened at `T`, not when the mistake was discovered.

**REVERSAL shape.** One `TransplantSourceLine` per source being restored (`source_plant_count` = the target's own frozen pre-event quantity, `discarded_plant_count = 0`), zero destination lines, zero allocations, one new `SeedlingSourceCheckpoint` per restored source (`remainder_after` = the same restored quantity). This reverses ALL source effects of the target (transferred quantity, damage, rejection, sample, other loss) — partial reversal is not supported; an optional REPLACEMENT re-declares the correct biological split. `enforce_transplant_reconciliation` gained a purely structural REVERSAL branch (`>=1` source line, zero destination/allocation) — RECORD/REPLACEMENT reconciliation is byte-for-byte unchanged.

**Checkpoint authority is the structural chain tip**, not `ORDER BY effective_time DESC` — the checkpoint for a `seedling_entry_id` that no other checkpoint names as its own `previous_checkpoint_id`. This is the one shared definition used everywhere "current checkpoint" is resolved (the Python-level resolver and every DB trigger use the identical `NOT EXISTS` shape), required because a REVERSAL's checkpoint legitimately shares its target's own `effective_time`, and a paired REPLACEMENT's checkpoint legitimately shares its REVERSAL's — `ORDER BY effective_time DESC` could no longer disambiguate once ties are legal. Both `enforce_seedling_source_checkpoint_insert_integrity`'s and `enforce_transplant_source_line_insert_integrity`'s own strict-monotonic effective-time checks gained one narrowly-scoped exception: EQUAL is legal only when the new checkpoint's own event is REVERSAL- or REPLACEMENT-kind — an ordinary independent RECORD remains strictly later, exactly as before this ticket.

**Restored assignment lifecycle.** A source the target fully exhausted (its assignment released) gets a brand-new `BatchCarrierAssignment` for the SAME physical Carrier — `opening_transplant_reversal_event_id` (the REVERSAL that opened it) and `restored_from_batch_carrier_assignment_id` (its immediate predecessor) — never a mutation of the original, released assignment, and never a second `SeedlingEntry` (`SeedlingEntry.batch_carrier_assignment_id` never repoints). A source the target never fully exhausted keeps using its own, still-active assignment directly. Either way, the checkpoint records the ACTUAL CURRENT assignment (the restored descendant, when one exists), resolved by every consumer (`_record_transplant_core`, Seedling Disposition, the biological Tray listing) via one shared, bounded backward-lineage walk (`app/services/seedling_source_lineage.py`) — arbitrary restoration depth is supported (original → restored → exhausted again → restored again → ...), guarded only defensively (structurally acyclic by construction: every opener/lineage column is immutable after INSERT). A restored assignment is a full, real biological source lifecycle: it supports a future Transplant, Seedling Disposition, partial use, full exhaustion, and a further correction, identically to an ordinary sowing-origin assignment — `released_by_transplant_event_id` is reused for every releaser (interpreting the releasing event's own `event_kind`: RECORD/REPLACEMENT exhaustion for a sowing-origin or reversal-restored source; REVERSAL closing only the destination it reverses), never a separate release column. Batch Derivation explicitly refuses to consume a reversal-restored assignment (`BatchDerivationValidationError`) — no new quantity semantics for it in this ticket.

**Eligibility**, proven under lock before any write: the Batch is active and its CURRENT active `BatchStageRun.id` still equals the target's own `active_batch_stage_run_id` (stage category alone is not sufficient); every source line's own checkpoint is still the structural chain tip (a later Transplant, Disposition, or other checkpoint activity on an involved source blocks correction); every target destination assignment is still unreleased (no downstream consumption, e.g. Batch Derivation, exists yet). An open Quality Hold does NOT block correction — deliberately, holds remain a stage-progression lock only. Physical Movement history does NOT block biological correction and is never touched by it — a wrong physical Table is a separate, ordinary Movement correction; supervisor recovery may be two-step (biological correction, then Movement if placement is also wrong). No atomic InterSalads correction wrapper exists yet.

**Idempotency.** The outer correction `client_command_id` is owned by the REVERSAL row. A REPLACEMENT's own `client_command_id` is deterministically derived (`uuid5`, mirroring `intersalads_transplant_service._derive_movement_client_command_id`'s precedent) from `(outer_client_command_id, target_event_id, "replacement")`. The correction fingerprint covers `target_event_id`, the normalized reason, and the replacement payload (or an explicit void marker) — deliberately never an effective_time, since none is caller-supplied.

**Permission.** `Permission.TRANSPLANT_CORRECT = "transplant.correct"`, granted to exactly `tenant_admin`, `farm_manager`, `head_grower`, `production_supervisor` — `transplant.manage` alone (the ordinary RECORD authority) is insufficient. Purely code-backed (no migration).

**Authoritative correction-chain read.** `POST /farms/{farm_id}/crop-batches/{batch_id}/transplants/{event_id}/correct` (biology only — no InterSalads/Movement fields, no caller-supplied effective time) returns `target_event`, a derived `status` (`voided`/`corrected`, no stored `is_current` boolean), `reversal_event`, `replacement_event` (nullable), and `reason`. The authoritative-chain resolver (`transplant_correction_service.resolve_authoritative_transplant`) walks: no REVERSAL for `E` → `E` is authoritative; a REVERSAL but no paired REPLACEMENT → voided (`None`); a paired REPLACEMENT → continue from it — bounded, with visited-id cycle protection (defensive only; structurally unreachable by construction).

## WORKFLOW-INTEGRITY-001 addendum: stage-exit remainder guard

Partial Transplant remains fully legal — a Tray may sit with positive remainder indefinitely while the Batch stays in a `transplanting`-category stage. What is no longer legal: leaving that stage while any of the Batch's `SeedlingEntry` sources still has positive **current source availability**. `crop_batch_service.transition_stage` gates this with a single check, inserted after the transition is already proven configured/valid (a bad `configured_transition_id` or stage mismatch still surfaces its own, more specific error first) and before the first write: if the *current* `BatchStageRun`'s `WorkflowStage.stage_category == "transplanting"`, every `SeedlingEntry` with `batch_id` equal to the transitioning Batch must read `current_source_available_count == 0` (via `seedling_disposition_service.get_unresolved_seedling_remainder`, which reuses `get_source_available` per entry — never a second, independently-derived balance formula). The guard never applies when leaving `seeding`, `germination`, `nursery`, `intermediate`, `production`, or any other category — at those points nothing has had a chance to resolve the source population yet (Transplant itself requires the `transplanting` category to run at all), so applying the guard there would make the very first stage advance of every Batch impossible.

**Current source availability** is exactly the existing checkpoint-chain-tip-plus-Disposition-delta authority (see the correction addendum above) — never `checkpoint.remainder_after` alone, since Seedling Disposition can independently drive it to zero without ever inserting a new checkpoint. Evaluated **as of the transition's own requested `effective_time`**, never wall-clock now — a biological resolution recorded after the requested transition time can never retroactively validate an earlier transition attempt. Destination biology (Nursery Cultivation Plates already holding living plants) and physical Movement/Occupancy never participate — only Seedling *source* availability is inspected. Restoration lineage (original → restored → restored again, TRANSPLANT-CORRECTION-001) never double-counts: the guard groups by `SeedlingEntry`, which is itself assignment-agnostic. Correction (Transplant REVERSAL/REPLACEMENT, Disposition REVERSAL/replacement) requires zero special-casing in the guard — it already flows through the same chain-tip/delta authority unchanged: a REVERSAL that restores positive remainder re-blocks exit; a REPLACEMENT that legitimately resolves it re-allows exit.

Serialization is the existing `CropBatch`-row-first lock every writer in this domain already acquires (`transition_stage`, `_record_transplant_core`, Transplant correction, Seedling Disposition record/correct) — no new lock was introduced.

**Follow-up landed — SEEDLING-DISPOSITION-LIFECYCLE-001:** the stranded-Carrier gap named above is now closed. See that ticket's own addendum below for the full Disposition-driven release/restoration lifecycle; `004B.2` operator UI remains gated on other, unrelated work, not this gap.

## SEEDLING-DISPOSITION-LIFECYCLE-001 addendum: Disposition-driven assignment release/restoration

**Exhausting Disposition releases the current assignment.** When a new `SeedlingDispositionEvent` (REDUCTION) drives authoritative source availability (`get_source_available` — the same checkpoint-chain-tip-plus-delta authority, never a competing formula) from positive to exactly zero, `seedling_disposition_service.record_disposition` releases the CURRENT active `BatchCarrierAssignment` in that SeedlingEntry's restoration lineage — never the SeedlingEntry's original, historical assignment if a restoration has since occurred. `released_effective_time` equals the REDUCTION's own `effective_time`; `released_by_seedling_disposition_event_id` (a third typed releaser, never reusing `released_by_transplant_event_id`/`released_by_batch_derivation_event_id`) names it. Partial Disposition never releases. A DB-level backstop (`enforce_batch_carrier_assignment_closure_only_v2`'s third branch) independently re-derives the SAME checkpoint-anchored formula to prove the releasing event genuinely leaves availability at zero — unreachable via direct SQL otherwise.

**Correcting an exhausting Disposition restores biology via a NEW assignment, never reactivating the predecessor** — identical discipline to Transplant correction above, reusing the SAME shared `restored_from_batch_carrier_assignment_id` lineage (never a parallel Disposition-only chain). The REVERSAL is the restoration opener (`opening_seedling_disposition_reversal_event_id`, unique per REVERSAL — Seedling Disposition targets exactly one source, unlike Transplant's many-to-many shape). Pure void (REVERSAL only) always creates and leaves the restoration assignment active. A corrected replacement that itself re-exhausts the source (zero → positive → zero) still creates the restoration assignment and then releases it by the replacement — never optimized away, since the replacement must become its own generation's typed exhaustion fact for any later correction of *it* to resolve unambiguously. Mixed Transplant/Disposition restoration generations (A → Transplant-restored B → Disposition-restored C → Transplant-restored D, in any order) are fully supported with zero special-casing, since the shared lineage-walking code (`seedling_source_lineage.py`) and every downstream consumer (`_record_transplant_core`, further Disposition, the biological Tray listing) are already opener-agnostic.

**The early "assignment must be active" gate is refined, not disabled**, at both the command-insert trigger and the event-insert trigger: if nothing in the lineage is currently active, a new command/event is permitted only when it is itself the CORRECT command (or its REVERSAL) reopening exactly what its own target released — resolved via the structural chain-TIP (`NOT EXISTS` successor, the same pattern already used for checkpoint chain-tip resolution), never merely "some assignment somewhere is active." Released by Transplant, Batch Derivation, or a *different* Disposition event remains rejected.

**Stage-run safety.** Every NEW `SeedlingDispositionCommand` (RECORD or CORRECT alike) records the CropBatch's currently-active `BatchStageRun.id` (`active_batch_stage_run_id`, mirroring `TransplantEvent.active_batch_stage_run_id`; DB-enforced non-null for new inserts, open-run, same tenant/farm/batch). Correction of ANY Disposition — exhausting or not, original REDUCTION or a prior correction's own replacement — requires the CropBatch to be active AND the current active run to still equal the target's own recorded run; this closes the exact gap WORKFLOW-INTEGRITY-001 could not retroactively guard (Disposition exhausts biology → Batch legitimately leaves `transplanting` → a later correction would otherwise silently restore living biology into a stage the Batch has already left). Historical (pre-migration) commands keep `active_batch_stage_run_id` NULL, deliberately never backfilled — correcting a legacy target is rejected outright (`SeedlingDispositionCorrectionStageContextUnavailableError`) rather than inferring stage context from the current assignment, current stage, or event `effective_time`.

**Carrier physical-use-order authority.** Neither `assigned_effective_time` (caller-backdatable, no cross-generation ordering enforced) nor `recorded_at` (transaction-start semantics, not commit order) nor restoration lineage alone (an unrelated new Sowing reusing a released Carrier sets no lineage link at all) can answer "has this physical Carrier been used by anything else since." `Carrier.latest_batch_carrier_assignment_id` is the authoritative, forward-only answer: it points to the most recently *created* `BatchCarrierAssignment` for that Carrier, maintained by exactly one centralized DB trigger (`maintain_carrier_latest_assignment_pointer`, `AFTER INSERT ON batch_carrier_assignments`) rather than duplicated across every Python creator. Release never moves it — only a new assignment's creation does. Backfilled once, at migration time, ONLY from each Carrier's currently-active assignment (unambiguous, since the pre-existing active-Carrier unique index already guarantees at most one) — no historical physical-use chronology before that point is reconstructed. Correcting an exhausting Disposition whose predecessor assignment A is being reopened checks `Carrier.latest_batch_carrier_assignment_id == A.id` under `Carrier FOR UPDATE` (terminal lock tier, acquired after `CropBatch`, matching the existing global lock order every assignment-creating writer already follows) — blocking permanently, even after a later reuse has itself since been released, since physical continuity was broken the moment anything newer claimed the Carrier. A historical use *before* A never matters, since A's own creation already overwrote the pointer.

**Boundaries preserved, not touched by this ticket:** Batch Derivation explicitly refuses a Disposition-restored assignment as a source (`BatchDerivationValidationError`), mirroring the existing Transplant-reversal rejection. Assignment release/restoration is purely biological — it never moves the physical Carrier, closes Occupancy, or grants sanitation approval; a Tray may sit with a released `BatchCarrierAssignment` while still physically occupying its Nursery location until an ordinary Movement removes it. No new audit event type — the existing `crop_batch.seedling_disposition_recorded`/`crop_batch.seedling_disposition_corrected` events gain additive `event_data` fields (`released_assignment_id`, `restored_assignment_id`, `replacement_released_assignment_id`) only when applicable. No permission change — `BIOLOGICAL_DISPOSITION_MANAGE` remains the sole gate for both RECORD and CORRECT; the pre-existing `farm_manager`/`head_grower` vs. `operator` authority asymmetry is out of scope here and tracked separately as `BIOLOGICAL-DISPOSITION-AUTHZ-001`.

## NURSERY-OPS-005A addendum: chained Transplant source authority (BatchCarrierPopulationCheckpoint)

**Problem closed.** Every addendum above still assumed a Transplant source is always `SeedlingEntry`-anchored (`SourceAssignmentHasNoSeedlingEntryError` otherwise). This categorically blocked a second, chained Transplant off a `nursery_cultivation_plate` destination a prior Transplant had just created — a real Nursery workflow (Seed Tray → Nursery Cultivation Plate → a further split/consolidation onto other Nursery Cultivation Plates) had no biological source authority to validate against. `SeedlingEntry`/`SeedlingSourceCheckpoint` are entirely UNCHANGED by this ticket — this is a genuinely separate, sibling authority, never a generalization of that one.

**Supported source Carrier types.** Exactly two, an explicit allowlist (`transplant_source_authority.ELIGIBLE_SOURCE_CARRIER_TYPE_CODES`), not a generic rule engine: `seed_tray` (unchanged `SeedlingEntry` path) and `nursery_cultivation_plate` (new `BatchCarrierAssignment`/`BatchCarrierPopulationCheckpoint` path, below). Any other Carrier type as a source — in particular `production_cultivation_plate` — is rejected with a dedicated typed error (`UnsupportedTransplantSourceCarrierTypeError`), checked before the generic "no biological authority resolvable" case. **Population authority never implies source eligibility**: a `production_cultivation_plate` destination genuinely holds a living population (its `TransplantDestinationLine.assigned_plant_count`, exactly like any other destination) but can never become a Transplant source — the ineligibility is Carrier-type-based, not population-based.

**Opening population for a normal (never-restored) `nursery_cultivation_plate` destination is derived, never stored.** No checkpoint row is inserted when such a destination is first opened — its opening population is read directly from its own `TransplantDestinationLine.assigned_plant_count`, anchored at the originating `TransplantEvent.effective_time`, exactly mirroring how `SeedlingEntry.starting_living_seedling_count` already anchors the Seed Tray path. The first checkpoint for such an assignment is written only once it is itself first CONSUMED as a source (see below).

**`batch_carrier_population_checkpoints`** is the sibling table to `seedling_source_checkpoints`, identical structural shape: `previous_checkpoint_id` self-FK chain, `UNIQUE(transplant_source_line_id)` (exactly one checkpoint per consuming source line), `UNIQUE(previous_checkpoint_id)` (branch prevention — the structural chain tip is always the row no other row names as its own predecessor, `NOT EXISTS`, never `ORDER BY effective_time DESC` — same rationale as the correction addendum above), `CHECK(remainder_after >= 0)`, composite tenant/farm FKs to `crop_batches`, `batch_carrier_assignments`, and `transplant_source_lines`. Anchored to `batch_carrier_assignment_id` directly — no separate "entry" identity exists for this authority; the `BatchCarrierAssignment` itself is the identity, so no restoration-lineage walk is needed (each restoration generation owns its own checkpoint chain, scoped by its own assignment id, unlike `SeedlingEntry` which is shared across an entire restoration lineage).

**Unified source-authority resolver** (`app/services/transplant_source_authority.py`) is the ONE place either checkpoint table is read or written from `transplant_service.py`/`transplant_correction_service.py` — a small internal discriminated `SourceAuthority` value object (`kind: "seedling_entry" | "batch_carrier_population"`), never a database authority-supertype table. `resolve_source_authority` dispatches purely on the source Carrier's type code; `get_source_available`/`append_source_consumption_checkpoint` dispatch on the resolved authority's own `kind`. Both authorities share the SAME consumption arithmetic (`available − allocated − damage − rejection − sample − other_loss = remainder_after`; zero releases via the assignment's own `released_by_transplant_event_id`); the `batch_carrier_population` authority simply has no Disposition-style delta ledger — its available quantity IS its anchor value directly.

**Chained consumption and exhaustion.** Consuming a `nursery_cultivation_plate` source behaves exactly like consuming a Seed Tray: partial consumption keeps the assignment active with a positive `remainder_after`; full consumption (`remainder_after == 0`) releases it via the same `released_by_transplant_event_id`/`released_effective_time` fields every other releaser uses; over-consumption is rejected before any write. A `production_cultivation_plate`-typed destination is never itself consultable this way — the service-layer allowlist above keeps it out of the source path entirely, so `enforce_batch_carrier_assignment_closure_only_v2`'s widened release-origin check (below) never has occasion to fire for it.

**Restoration mirrors the Seed Tray path exactly.** Correcting a chained consumption that fully exhausted a `nursery_cultivation_plate` source creates a brand-new `BatchCarrierAssignment` for the SAME physical Carrier (`opening_transplant_reversal_event_id`, `restored_from_batch_carrier_assignment_id`) — never a mutation or reactivation of the original, released assignment. The REVERSAL synthesizes its own `TransplantSourceLine` (`source_batch_carrier_assignment_id` = the new restored assignment, `source_plant_count` = the amount originally consumed), then inserts exactly one `BatchCarrierPopulationCheckpoint` for it (`remainder_after` = the restored population, `previous_checkpoint_id = NULL` — a fresh chain, since this is a new assignment identity) — the exact same checkpoint-synthesis pattern the Seed Tray restoration path already used, applied to the sibling table. Multi-generation restoration (A exhausted → B restored → B exhausted → C restored → ...) is fully supported with zero special-casing, since each generation is simply its own assignment with its own checkpoint chain.

**Carrier-reuse protection, extended to every Transplant correction restoration path — including the pre-existing Seed Tray one, which previously had no such protection at all.** Before creating any restored assignment, the Carrier is locked and `Carrier.latest_batch_carrier_assignment_id` is proven still to equal the assignment being restored; a mismatch raises `TransplantCorrectionCarrierReusedError`, permanently — even if the later, physically-reusing assignment has itself since been released (physical continuity was broken the moment anything newer claimed the Carrier, mirroring `SEEDLING-DISPOSITION-LIFECYCLE-001`'s own Carrier-physical-use-order authority exactly).

**Correction chain-tip eligibility** extends unchanged: a `nursery_cultivation_plate` source is correctable only while its own checkpoint is still the structural chain tip — a later Transplant, correction, or other checkpoint activity on it blocks correction, exactly like the Seed Tray path. Physical Movement alone is never biological consumption and never blocks correction.

**Locking.** No lock-order change anywhere. Creation operations (a fresh destination assignment) keep the existing Carrier-first lock, post-lock revalidation, then create; existing-assignment operations (consuming an existing source, correcting) keep the existing assignment-first lock. Two concurrent consumers of the same `nursery_cultivation_plate` source serialize on that assignment's own row lock exactly as two concurrent consumers of the same Seed Tray already did — proven never to create a competing checkpoint chain branch (`test_batch_carrier_population_checkpoint_concurrency.py`).

**Production-entry workflow-stage guard, distinct from and additional to the pre-existing WORKFLOW-INTEGRITY-001 leaving-transplanting guard (unchanged, still governs only leaving a `transplanting`-category stage).** A NEW guard fires only on an explicit transition whose configured destination stage has `stage_category == "production"`: it rejects the transition (`BatchStageHasUnresolvedPreProductionRemainderError`) while the Batch still has (a) any `SeedlingEntry`-backed unresolved living population, or (b) any ACTIVE `nursery_cultivation_plate` population-authority remainder — released/zero-remainder assignments are excluded, and `production_cultivation_plate` population never participates (by design: production placement is the very thing this guard gates entry to, not a pre-condition of it). **Mixed placement remains fully legal** — a Batch may have living population on both a Nursery Cultivation Plate and a Production Cultivation Plate simultaneously while still pre-production-stage; the guard blocks only the explicit stage transition, never the physical Transplant itself, and Transplant never auto-transitions stage. Within this ticket's own scope, biology chained purely Nursery-Plate-to-Nursery-Plate can never fully resolve this guard on its own — it always ends up on some active Nursery Plate; genuine resolution (moving biology onto Production placement in a way this guard recognizes) is NURSERY-OPS-005B's scope, not this ticket's.

**Deferred to NURSERY-OPS-005B:** the Leafy Production operator UI/API, any `production_cultivation_plate` → `grow_table` occupancy compatibility, and any read endpoint surfacing this new population authority directly.
