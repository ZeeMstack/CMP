# Crop-Batch Split and Merge Lineage Model

Full detail: `CMP_MASTER_SPEC.md` §2, §8; `CLAUDE.md` rules 1, 3, 4, 5, 6, 7, 8, 9, 10, 12. This document summarizes the approved model as implemented in CMP-012; it does not restate the spec.

## Scope

CMP-012 is the first command that changes **crop-batch identity** rather than a batch's stage or carriers. A split turns one active batch into two or more new active batches; a merge turns two or more compatible active batches into one new active batch. In both cases every active carrier assignment moves whole — the same physical carrier, complete contents, one new assignment — from a source batch to an output batch; no carrier is ever split between outputs, no quantity is edited, and no plant is discarded. Out of scope: partial carrier-content splitting, quantity adjustment, discard, batch-to-batch plant allocation independent of carriers, combining incompatible workflow versions, cross-farm/cross-tenant derivation, carrier movement, occupancy changes, automatic stage progression, transplantation, harvest, packing, inventory deduction, costing, reversal, void, correction, and reopening a superseded batch.

## Superseded lifecycle

A crop batch gains a third terminal state, `superseded`, alongside `active`/`closed`. `superseded_effective_time` and `superseded_by_batch_derivation_event_id` are present if and only if `state = 'superseded'`; `closed_effective_time` remains NULL. Allowed transitions are `active → closed` (CMP-008, unchanged) and `active → superseded` (CMP-012); `closed → superseded`, any transition out of `superseded`, and reopening are all rejected by a CMP-012 lifecycle trigger (`enforce_crop_batch_lifecycle_v2`) that supersedes CMP-008's original trigger attachment without editing its function body. A superseded batch's final stage run is never closed and no fabricated closing transition is created — it remains the batch's permanent historical current-stage context, exactly like a closed batch's terminal run. Every existing command that already checks `state != "active"` (sowing, transplantation, observations, stage progression, quality-hold placement/release) rejects a superseded batch automatically, with no code change required.

## Conditional command ownership

A `batch_derivation_event` — not each output batch — owns idempotency for a split or merge. `crop_batches.client_command_id`/`request_fingerprint` are conditionally nullable: non-null and required for a directly created batch (`created_by_batch_derivation_event_id IS NULL`), null for a derivation-created output (`created_by_batch_derivation_event_id IS NOT NULL`), enforced by a CHECK. No per-output command UUID is ever fabricated. The same shape applies to `batch_stage_transitions`, which gains a third `command_kind`, `derivation_entry`: an internal provenance record (`batch_derivation_event_id` set, `client_command_id`/`request_fingerprint` null, `source_stage_id`/`configured_transition_id` null, `destination_stage_id` = the event's inherited stage) opening each output batch's one and only active stage run — never a client-facing command, never a fabricated configured transition. The public `POST /crop-batches` and stage-transition endpoints are unchanged and still require a client command ID in every request.

## Derivation event, source/output/transfer lines

One `batch_derivation_event` is one split or merge command (`derivation_kind IN ('split', 'merge')`), carrying the workflow/version/inherited-stage every output must match. `batch_derivation_sources` (one row per consumed source batch; `source_batch_id` globally unique — a batch may be superseded by at most one successful derivation event, ever) and `batch_derivation_outputs` (one row per created output batch; no `output_batch_code` column — the code lives once, immutably, on `crop_batches.code`) record per-batch quantity/carrier-count totals. `batch_assignment_transfers` is the actual carrier-level record: one row per transferred carrier, naming the released source assignment and opened destination assignment (each globally unique — one transfer per assignment, ever), the immutable transferred plant count, and the exact source/output batch pair.

## Quantity derivation and chaining

Transferred quantity is always server-derived, never client-supplied, by branching on the source assignment's opener: sowing-origin reads `sowing_event_lines.sown_site_count`; transplant-origin reads `transplant_destination_lines.assigned_plant_count`; **derivation-origin** (an assignment itself opened by a prior split/merge) reads that assignment's own `batch_assignment_transfers.transferred_plant_count` — one hop back, regardless of chain depth. This makes chained lineage safe by construction: `batch_carrier_assignments` gains a third opener (`opening_batch_derivation_event_id`) and second releaser (`released_by_batch_derivation_event_id`), widening the exactly-one-opener CHECK to three columns. Unlike transplant-release (still sowing-origin-only, unchanged), derivation-release has no origin restriction — sowing-, transplant-, and derivation-origin assignments are all transferable. Cycle prevention is structural, not an extra mechanism: every output is a brand-new batch minted inside the transaction (never an existing batch), every source must already exist and be active, and supersession is one-time and terminal — a batch can never become its own ancestor.

## Compatibility, holds, and locking

Split requires exactly one active source with at least two active assignments, mapped completely and exactly once across at least two new outputs. Merge requires at least two active sources sharing the same tenant, farm, workflow, workflow version, and current stage, with every active assignment from every source transferred to the single new output. An open quality hold on any source blocks the whole command (checked after idempotency replay, before mutable-state validation) — unlike transplantation, split/merge would otherwise let an operator bypass a hold by replacing the held batch's identity. Locking is deterministic and UUID-sorted throughout: source batch(es), their active stage runs, active source assignments, then carriers.

## Deferred database validation

Service-level validation is insufficient by itself. One function, `enforce_batch_derivation_reconciliation`, is attached via ten `DEFERRABLE INITIALLY DEFERRED` constraint triggers across every mutation point in a derivation's lineage (event/source/output/transfer inserts; output crop-batch insert; source supersession update; derivation-entry transition insert; output stage-run insert; source-assignment release update; destination-assignment insert). All ten resolve to the same event and re-validate its complete state at real commit — split/merge cardinality, source/output completeness, workflow/version/stage inheritance, and full quantity reconciliation (per-source, per-output, and grand totals) — catching a later, separate transaction's direct-SQL tampering against an already-committed event, exactly like CMP-011's `enforce_transplant_reconciliation`.

## Database protection and downgrade guard

Composite foreign keys prove tenant/farm consistency structurally throughout. The CMP-011 `batch_carrier_assignments` insert-integrity and closure-only functions, and the CMP-008 `crop_batches` lifecycle function, are left completely untouched — only their trigger attachments were dropped and replaced with CMP-012-named `_v2` triggers/functions, so downgrade restores each prior ticket's exact behavior by re-attaching a trigger to its original, never-modified function. All four new tables are append-only/no-delete. Downgrading past CMP-012 is destructive by nature; the migration's `downgrade()` queries, before any DDL, for any `batch_derivation_events` row, any derivation-created or superseded crop batch, any `derivation_entry` transition, or any derivation-opened/released assignment — if any exist, it raises `RuntimeError` and aborts with zero schema change.

## Deferred

Partial carrier-content splitting, quantity adjustment, discard, cross-farm/cross-tenant derivation, carrier movement/occupancy changes, automatic stage progression, reversal, correction, reopening a superseded batch, a general transformation engine, harvest, packing, inventory deduction, costing, frontend, RLS, role-specific authorization.
