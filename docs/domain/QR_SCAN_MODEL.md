# QR Identifier and Scan Context Model

Full detail: `CLAUDE.md` rules 2, 7, 10, 11, 12; `docs/adr/006-scan-identity-tokens.md`; the PILOT-SCAN-001 ticket ("QR identities, label printing & scan context"). This document summarizes the approved model; it does not restate the ticket.

## Core rule

**QR identifies context. Scanning never executes a farm operation.** Resolving a token only returns a typed read of current state and prepared navigation links — it never moves plants, completes a Work Item, records Harvest/loss, releases Quality, puts away inventory, records an Observation, or performs any other business transaction. Every destination a scan links to independently re-resolves/validates the ids it was given; QR resolution is never authorization for the downstream command.

## What a QR Identifier is, and is not

A `QrIdentifier` (`qr_identifiers` table) is this ticket's concrete implementation of ADR 006's `scan_identity` concept: it links an opaque, server-generated public `token` to exactly one of eight supported entities. It stores **no mutable operational fact** — never crop, variety, location, status, quantity, current Batch occupant, or Quality state. Those are read fresh from the authoritative live tables every time a token is resolved (`qr_service.resolve_scan_context`).

One typed nullable FK column per supported entity type (`crop_batch_id`, `location_id`, `carrier_id`, `asset_id`, `batch_carrier_assignment_id`, `harvested_produce_lot_id`, `graded_produce_lot_id`, `finished_goods_lot_id`), mirroring `FarmWorkItem`'s own structured-context precedent (PILOT-OPS-001) — real composite FKs, never a bare polymorphic `entity_id` with no referential integrity. `entity_type` is a redundant, CHECK-enforced discriminator naming exactly which one is populated.

A CURRENT-STATE row (ADR-005), like `CropBatch`/`FarmWorkItem`: identity/content fields (tenant/farm, entity_type, every typed entity column, token, `created_by_user_id`/`created_at`) are frozen for life by a DB trigger (`enforce_qr_identifier_mutable_fields`); only `status`/`revoked_at`/`revoked_by_user_id` may ever change. No hard delete is possible.

## Token design

`secrets.token_urlsafe(24)`, server-chosen, opaque, globally unique (`ux_qr_identifiers_token`). The QR payload is `<canonical app origin>/q/<token>`, where the canonical origin is resolved server-side from `APP_BASE_URL` (`lib/server/same-origin.ts::resolveTrustedOrigin`, the same value Auth0's own trusted-redirect logic already uses) — **never** `window.location.origin`. A permanent printed label must point at the one canonical GrowCMP web origin for its whole physical lifetime, regardless of which hostname the operator happened to open (a Render preview URL, a LAN IP, localhost) when they printed it. Because `APP_BASE_URL` is deliberately server-only (never `NEXT_PUBLIC_*`), the label preview route (`app/farms/[farmId]/labels/[entityType]/[entityId]/page.tsx`) is a Server Component that resolves the origin and passes it down as a plain prop to the Client Component that renders the label/QR (`LabelPreviewClient.tsx`); if `APP_BASE_URL` is unset/invalid, the origin resolves to `null` and the label preview refuses to render a QR at all rather than falling back to any request- or browser-derived value. The token is an **identifier, not an authorization grant**: every resolve still goes through the caller's authenticated tenant/permission context; a valid token belonging to an inaccessible tenant returns the identical generic 404 a nonexistent/revoked token does (never an existence oracle).

## Permanent vs. operational identity

- **Permanent** (Carrier, Asset, Location): the QR stays with the physical object/place for its life. The printed label never prominently shows a mutable fact (current Batch/location/status) — the scan page resolves those dynamically.
- **Operational** (Crop Batch, Batch Carrier Assignment/"Placement", Harvested Produce Lot, Graded Produce Lot, Finished Goods Lot): identifies an operational record. May print stable creation-time metadata (crop/variety) on the label; never current stage/status.

**Batch vs. placement** are never merged. A Batch may occupy several Carriers/Locations at once; scanning "the Batch" cannot tell an operator which physical portion they are standing beside. `BatchCarrierAssignment` (CMP-006's own "what crop batch does this carrier contain right now" identity) is the stable, independently-scannable placement identity — its own QR resolves the exact Batch sub-context (crop/variety, current location via its Carrier's own current occupancy), never collapsed into the parent Batch's QR.

**Carrier permanence**: a reusable Carrier's QR (e.g. a Production Cultivation Plate) identifies the physical object, never today's occupant. Scanning it resolves the CURRENT Batch/location dynamically (via `sowing_service.get_carrier_batch_assignment`/`movement_service.get_resolved_location`) — tomorrow the same Carrier may carry a different Batch, and the same QR resolves that new fact automatically.

## Idempotent generation

`qr_service.generate_or_get_qr_identifier` returns the entity's one active identifier, creating it only if none exists. Concurrent callers racing to create the first identity for the same entity never both win: the loser's INSERT hits one of eight partial unique indexes (`ux_qr_identifiers_active_<column>`, `WHERE status = 'active'`, mirroring `Occupancy`'s own XOR-uniqueness pattern), and the service simply re-reads the row the winner just committed. Reprinting reuses this same identity — it never creates a new QR, a new Batch/Lot/Carrier, or a new operational event.

## Automatic provisioning at creation (PILOT-SCAN-001D)

**Permanent Physical Identity is frozen: a Location, Carrier, or Asset gets its permanent QR identity automatically the moment it is created — never a manual "Generate QR" step, and never later than the creation command's own commit.** `qr_provisioning.py` (`app/services/qr_provisioning.py`) is a small, dependency-free leaf module — it depends only on the `QrIdentifier` model and `audit.append_audit_event`, deliberately with NO dependency on `carrier_service`/`location_service`/`asset_service` (unlike `qr_service.py`, which needs those three for its own `_require_entity_exists`/scan-resolution responsibilities) — so those very services can import it without a circular import (`qr_service` already imports them the other way).

`qr_provisioning.ensure_qr_identifier_for_new_entity` is called from inside every current Location/Carrier/Asset creation path, immediately after the entity is flushed and BEFORE that command's own single commit — never a separate, earlier commit of its own. This means the entity and its permanent QR always succeed or fail together, atomically, in whichever transaction that creation command already uses:

- `carrier_service.register_carrier` / `bulk_register_carriers`
- `location_service.create_location` / `bulk_generate_children`
- `asset_service.register_asset`
- `farm_setup_service.create_greenhouse_setup` — a composite command that creates many Locations/Assets (Zones, Spans, Tables/Gutters/Bag Positions, Germination Trolleys, Seeding Machines) in ONE transaction; every one of them gets its own QR in that same one commit, not the Greenhouse alone.

Unlike `generate_or_get_qr_identifier` (which must handle a genuine concurrent race — two callers racing to be the first to QR-provision an *already-existing* entity, e.g. two simultaneous "Print Label" clicks), `ensure_qr_identifier_for_new_entity` never needs that dedup-check/`IntegrityError`-retry dance: the `entity_id` it is given is a UUID freshly generated for a row no other session can see until this transaction commits, so no concurrent caller can already hold — or be racing to create — a `QrIdentifier` for it. If the INSERT itself somehow fails, the exception propagates naturally and aborts the whole creation command: physical master data must never silently end up without its permanent QR. Both functions share one low-level insert primitive (`qr_provisioning.insert_qr_identifier`) so the actual `QrIdentifier(...)` construction is never duplicated.

The QR never changes because the Batch occupant changes, the location changes, status changes, specification metadata changes, the resource becomes empty, or it is cleaned/reused for a different Batch — none of those are the entity's own identity, and this hook only ever fires once, at creation.

### Backfill for existing master data

`qr_service.backfill_missing_permanent_qr_identifiers` (invoked by `scripts/backfill_permanent_qr_identifiers.py`) ensures every Location/Carrier/Asset that existed *before* this automatic hook existed ends up with exactly one active QR too — without an operator opening hundreds of records by hand. It reuses `generate_or_get_qr_identifier` per missing entity (never a bespoke insert), so it is safe to rerun: an entity that already has an active QR (from a prior backfill run, or from the ordinary creation-time hook) is simply skipped, and a genuine concurrent race (an operator's real "Print Label" click landing on the same pre-existing entity at the same moment) is handled by that function's own existing `IntegrityError` fallback. Each entity is provisioned independently — one entity's failure (e.g. a farm that has since gone inactive) is recorded and does not abort the rest of the run. `--dry-run` only counts what is missing and never calls the provisioning function at all (which commits per entity, so a caller-side rollback afterward could not undo it). The script itself is never executed by Claude against a real/production database — running it there is a manual operator action, exactly like `scripts/manage_platform_admin.py`.

## Scan resolution and authorization

`GET /qr/{token}` returns a compact, discriminated `ScanContext` (one Pydantic model per `entity_type`, never one giant universal object). Authorization here deliberately does not fit this codebase's usual single-static-`Permission`-per-route shape (see `test_authz_read_enforcement_architecture.py`'s own exemption mechanism): a generic resolver's real permission requirement is only known after the token resolves to an `entity_type`. Every QR route (`GET /qr/{token}`, `POST /farms/{farm_id}/qr/{entity_type}/{entity_id}/generate`, `POST /qr/{token}/print`) requires `require_tenant_context` (real authentication + active membership), then enforces the exact per-entity-type `Permission` via `has_permission()` inside the route body before any content is returned or write happens.

`ENTITY_PERMISSIONS` (`app/api/qr.py`) is a FROZEN mapping, verified against the live route table (never a plausible guess) for every one of the eight entity types:

| entity_type | read permission | manage permission | verified against |
|---|---|---|---|
| `crop_batch` | `crop_batch.read` | `crop_batch.manage` | `GET .../crop-batches/{id}` (`app/api/crop_batches.py`) |
| `location` | `location.read` | `location.manage` | `GET .../locations/{id}` (`app/api/locations.py`) |
| `carrier` | `carrier.read` | `carrier.manage` | `GET .../carriers/{id}` (`app/api/carriers.py`) |
| `asset` | `asset.read` | `asset.manage` | `GET .../assets/{id}` (`app/api/assets.py`) |
| `batch_carrier_assignment` | `sowing.read` | `sowing.manage` | `GET .../carriers/{id}/batch-assignment`, `GET .../crop-batches/{id}/carriers` (`app/api/sowings.py`) |
| `harvested_produce_lot` | `harvest.read` | `harvest.manage` | `GET .../harvested-produce-lots/{id}` (`app/api/harvests.py`) |
| `graded_produce_lot` | `grading.read` | `grading.manage` | `GET .../graded-produce-lots/{id}` (`app/api/grading.py`) |
| `finished_goods_lot` | `packing.read` | `packing.manage` | `GET .../finished-goods-lots/{id}` (`app/api/packing.py`) |

Two corrections from this ticket's own first draft, caught at final closure: `batch_carrier_assignment` is gated by `sowing.*`, not `crop_batch.*` — CMP-006's own BatchCarrierAssignment read/write authority already lives under Sowing (`sowing_service.list_batch_carriers`/`get_carrier_batch_assignment`, the exact two functions `qr_service` calls for this entity type, are `sowing.read`-gated). `finished_goods_lot` is gated by `packing.*`, not `finished_goods_storage.*` — `packing_service.get_finished_goods_lot` (the exact function `qr_service` calls) is exposed under `packing.read` in `app/api/packing.py`; `finished_goods_storage.*` governs physical cold-store custody/movement, a different concern this entity type's own identity read never touches.

`tests/test_qr_authz.py` is a single parametrized test proving, for all eight entity types: an authorized same-tenant user resolves it; a role holding every `.read` but no `.manage` permission (`qc_officer`) can never generate/print any of them; a role lacking most `.manage` and five of the eight `.read` permissions (`storekeeper`) is denied both, using the genuine existing role policy (never weakened to make the test pass) — including the honest fact that `location.read`/`carrier.read`/`asset.read` are granted to every current role, so no read-bypass negative exists for those three; a foreign tenant is denied (scoped 404); and a corrupted token never leaks whether the underlying entity exists.

## Print/reprint audit

Tracked via the existing `AuditEvent` infrastructure (`entity_type = 'qr_identifier'`, `action = 'qr_label_print_requested'`) — no separate print-event table. The action name and the response field (`PrintLabelResponse.requested_at`, not `printed_at`) are deliberate: a browser print dialog cannot prove a physical label actually came out of a printer, so the audit trail only claims what is actually known — that a print was requested. "Initial print"/"reprint" mean "first print request"/"subsequent print request for the same active QR identity", adequate for pilot audit, never a physical-output guarantee; the frontend's own confirmation text says "requested", never "printed"/"recorded". `is_reprint` is derived server-side from whether a prior print *request* already exists for that QR identity, never accepted from the caller. A reprint of an operational/lot label (Crop Batch, Batch Carrier Assignment, Harvested/Graded Produce Lot, Finished Goods Lot) requires a non-blank `reason` (`QrReprintReasonRequiredError`, mapped to 400) — a permanent Carrier/Asset/Location label's reprint never requires one.

## Scan ≠ activity

A QR scan is not proof that farm work occurred. No Harvest/Movement/Observation/other business event is ever created merely from resolving a token. "Recent activity"/history for a scanned Batch/Location links to the existing traceability/movement/observation surfaces (via prepared `actions`) rather than duplicating a second generic activity ledger — see `docs/product/OPEN_QUESTIONS.md` for the aggregation gap this leaves open.

## Label-only printing (PILOT-SCAN-001B)

`window.print()` on an in-app page prints that whole page's DOM — nav, breadcrumbs, header, and every on-screen control alongside the label. Every "Print Label(s)" action in the app instead opens a dedicated print-only document, `/print/labels?items=<url-encoded JSON array of PrintableLabel>` (`app/print/labels/page.tsx` + `PrintLabelsClient.tsx`), which renders outside the `/farms/[farmId]/*` `AppShell` layout tree entirely (the same pattern already used for `/q/[token]`) — a dedicated print-only layout, never per-selector `@media print` hiding of an app page. `openLabelPrintWindow` (`lib/labels/printableLabel.ts`) builds that URL and calls `window.open` **synchronously**, within the same click-handler call stack that triggered it, so no browser treats it as an unrequested popup; this requires every QR token the print job needs to already be resolved before the click (see `usePreparedPrintLabels` below) — an async fetch inside the click handler would make the resulting `window.open` call async and get silently blocked. `PrintLabelsClient` calls `window.print()` itself, once, in a `useEffect` after the labels are rendered — this is still the one browser print dialog the operator's own click already asked for, not a second, silent print.

**PILOT-SCAN-001C production fix:** `app/print/labels/page.tsx` has no dynamic path segment (unlike `/farms/[farmId]/labels/[entityType]/[entityId]`, which Next.js already renders on demand per params), so with nothing else to opt it out of static rendering, Next.js prerendered it once at BUILD TIME — `resolveTrustedOrigin()` ran during the build and its one result (built with whatever `APP_BASE_URL` the build step happened to see) was baked into the static HTML served for every later request, regardless of the correctly-configured runtime `APP_BASE_URL`. `export const dynamic = "force-dynamic";` on that page forces it to render fresh per request, so `resolveTrustedOrigin()` always reads the live runtime environment — no change to `resolveTrustedOrigin()` itself, no new env var, no hardcoded origin.

`PrintableLabel` (`lib/labels/printableLabel.ts`) is the one small, JSON-serializable shape every caller builds: `{ token, size, entityType, entityTypeLabel, code, lines }`. A single print job may legitimately mix SMALL (50×30mm, Permanent Carrier/Asset/Location labels) and STANDARD (100×60mm, Batch/placement/operational labels) templates in one document — e.g. a Batch Master Label alongside several Tray labels from one Sowing. Since CSS `@page { size }` is document-global rather than scoped per element, `PrintLabelsClient` addresses each label's physical page size via **named pages** (`@page label-small`, `@page label-standard`, selected per label via the CSS `page` property) rather than nesting multiple conflicting `@page` rules.

`requestPrintAudit`/`printLabels` (`lib/labels/printableLabel.ts`) record one `qr_label_print_requested` audit event **per label** via the existing `POST /qr/{token}/print` API — the same primitive `LabelPreviewClient.tsx`'s own single-label reprint button already used, never a new/generic page-level event. `printLabels(labels)` is the one call every stage-label "Print Labels" button makes: it opens the print window first (synchronously, popup-blocker-safe), then fires each label's own print-request call, deliberately un-awaited and with any failure swallowed — a slow/failed audit call must never gate, delay, or reverse the print action that already opened. `reason: null` is always correct here: every one of these labels was generated in the same operation that is printing it for the first time, so the backend's own `is_reprint` bookkeeping reads `false` and never demands a reason.

## Operational stage labels and `OperationalLabelContext` (PILOT-SCAN-001B)

Distinguishes, on top of PILOT-SCAN-001's existing Permanent/Operational identity split:

- **Batch Master Label**: QR `entity_type = "crop_batch"`. Identifies the Batch itself. Printed once per Batch (Sowing success); never printed as the sole identifier across every tray/plate — a Batch may occupy several carriers/locations at once.
- **Permanent Carrier Label**: QR `entity_type = "carrier"` — PILOT-SCAN-001's original generic label. Identifies the reusable physical object itself, for its whole life, regardless of which Batch it currently holds.
- **Operational Placement Label / Stage Label**: identifies ONE specific physical carrier/placement (Seed Tray, Nursery/Production Cultivation Plate, Grow Cube, Grow Bag) with a print-time snapshot of the Batch/stage/location context it currently holds.

**PILOT-SCAN-001B FINAL CLOSURE — entity selection rule for the Operational Placement Label's QR:** the QR identifies the strongest existing stable Batch-placement identity available from that stage's own authoritative result/read model — `entity_type = "batch_carrier_assignment"` — never the reusable Carrier's own permanent identity. The reason this distinction matters: a Carrier is reusable — the same physical Seed Tray/Plate/Cube/Bag can later hold a *different* Batch. `BatchCarrierAssignment` rows are immutable-history, current-state rows (ADR-005, CLAUDE.md rule 7): a new occupancy of the same Carrier by a different Batch always opens a brand-new `BatchCarrierAssignment` row with its own id — it never mutates an existing row's `batch_id`/`carrier_id`. `qr_service.resolve_scan_context`'s `batch_carrier_assignment` branch (`app/services/qr_service.py`, unchanged since PILOT-SCAN-001) fetches the assignment row **by its own id** and reads `assignment.batch_id`/`assignment.carrier_id` directly off that specific row — never "whichever assignment the Carrier currently has." A placement QR printed today therefore keeps resolving today's Batch for its whole physical life, even after the same tray is washed and resown for a different Batch next season; a Carrier QR printed for the same physical object would instead follow the Carrier and silently start resolving the new occupant. This property is a pre-existing, unmodified guarantee of PILOT-SCAN-001's own backend code (proven here by direct code inspection of `qr_service.py` lines 473–497, not a new backend test run, since no backend code changed in this closure).

Per-stage entity selection (verified against each stage's own actual authoritative result/read model, never assumed uniform):

| Stage | Physical carrier | Stable placement id available? | QR entity used | Why |
|---|---|---|---|---|
| Sowing | Seed Tray | Yes — `SowingEventLineRead.batch_carrier_assignment_id` | `batch_carrier_assignment` | The sowing command's own result returns it directly |
| Germination placement | Seed Tray | Usually — not from `place_tray`'s own response (`TrayPlacementRead` carries no assignment id), but from the already-loaded Germination worklist read (`GerminationTrayRead.batch_carrier_assignment_id`), which the frontend already has for this exact tray and which is unchanged by the Movement | `batch_carrier_assignment` when found; **no Operational Placement Label is generated at all if it cannot be found** | Uses an already-authoritative, already-fetched value rather than inventing one; never a backend change, and never a Carrier-QR fallback (see below) |
| Seedling entry | Seed Tray (same physical tray as Germination) | Yes — `SeedlingEntryRead.batch_carrier_assignment_id` | `batch_carrier_assignment` | Command's own result returns it directly |
| InterSalads | Nursery Cultivation Plate | Yes — `IntersaladsDestinationLineRead.destination_batch_carrier_assignment_id` | `batch_carrier_assignment` | Command's own result returns it directly |
| Leafy Production | Production Cultivation Plate | Yes — `LeafyProductionDestinationLineRead.destination_batch_carrier_assignment_id` | `batch_carrier_assignment` | Command's own result returns it directly |
| InterVines | Grow Cube | Yes — `IntervinesGrowCubePlacementRead.destination_batch_carrier_assignment_id` | `batch_carrier_assignment` | Command's own result returns it directly |
| Vines Production | Grow Bag | Yes — `VinesProductionGrowBagPlacementRead.destination_batch_carrier_assignment_id` | `batch_carrier_assignment` | Command's own result returns it directly |

**No implicit fallback between the three label identity meanings.** An earlier revision of this closure had Germination placement fall back to the Carrier's own permanent QR (`entity_type = "carrier"`) when `rows.find(r => r.trayId === receipt.trayId)` found no matching row. That fallback has been removed: an Operational Placement/Stage Label representing Batch + Seed Tray + Germination placement must never silently become a permanent Carrier QR, because a later, unrelated Batch's occupancy of the same reused Carrier would then resolve as if it were this placement — exactly the ambiguity `batch_carrier_assignment` exists to prevent. If the lookup genuinely fails, `GerminationReceiptCard` (`app/farms/[farmId]/nursery/germination/page.tsx`) generates NO Operational Placement Label at all: no QR is generated of any entity type, no "Print Tray Label" button is even offered, and the operator instead sees "Placement identity is not available yet. Refresh before printing." with a Refresh action that re-fetches the worklist via existing data mechanisms (never a guessed assignment, never a newly-created one). A separate, explicitly-labelled "Print Carrier Label instead" link remains available in that state, pointing at the existing generic Carrier label route (`/farms/[farmId]/labels/carrier/[carrierId]`) — a different label type, never presented as this placement's label.

`lib/labels/operationalLabel.ts` is the one small `OperationalLabelContext` builder module (`{ size, entityTypeLabel, code, lines }`) — presentation composition only, never a new source of domain truth, and deliberately QR-entity-agnostic: which QR entity backs a label (above) is decided by each page's own call site, independent of this shared content-formatting module. One function per stage: `batchMasterLabel`, `sowingTrayLabel`, `germinationPlacementLabel`, `seedlingEntryLabel`, `intersaladsPlacementLabel`, `leafyProductionPlacementLabel`, `intervinesPlacementLabel`, `vinesProductionPlacementLabel`. `lib/labels/usePreparedPrintLabels.ts` resolves each spec's QR token (idempotent `generate_or_get_qr_identifier`, unchanged from PILOT-SCAN-001) in the background as soon as a success screen renders, producing the `PrintableLabel[]` a "Print Labels" click hands to `printLabels`.

Mandatory entry points, each adding a "Print Labels" action immediately after the operation already succeeded (never before, never gating/blocking/reversing it on a print failure): Sowing (Batch Master Label + one Tray label per sown tray), Germination placement, Seedling entry, InterSalads transplant, Leafy Production transfer, InterVines transplant, Vines Production transfer.

Two deliberate content constraints, enforced by construction in `operationalLabel.ts` and covered by its own tests: Leafy Production's placement label never carries the source Nursery Cultivation Plate's identity forward (Nursery Plates never move into Production — the label always names the destination Production Cultivation Plate the transfer command itself created); InterVines's placement label never references a Grow Bag (Grow Bags do not exist until Vines Production).

**Known gap** (Vines Production only, tracked in `docs/product/OPEN_QUESTIONS.md`): `VinesProductionTransferRead` exposes only a bare Grow Gutter code for the destination — no Greenhouse/Zone/Span breakdown, and no per-Grow-Bag link back to a specific source Grow Cube. The Vines Production placement label uses exactly what is authoritatively available (Batch, Grow Bag, Gutter, plant count) rather than guessing or inventing either fact.

## Reprint Current Label (PILOT-SCAN-001B FINAL CLOSURE)

An operator whose current Germination/Seedling/Production label is damaged needs to reproduce the CURRENT applicable operational label — not a historical one, and not a second, separate reprint mechanism. This reuses PILOT-SCAN-001's own generic label preview/reprint route (`/farms/[farmId]/labels/batch_carrier_assignment/[assignmentId]`) unchanged in mechanism: it already resolves the SAME active QR identity (idempotent `useQrIdentifierFor`) and re-resolves current authoritative state fresh via `useResolveQr` (`staleTime: 0`) every time it is opened — so if the placement has since moved to a new stage, the reprinted label reflects that new stage's own current facts, never the stale snapshot from when it was first printed; if it has since been released, it says so instead of showing a stale location. It creates no movement/transformation and no new Batch/placement — it is a pure read.

`lib/labels/labelContent.ts`'s `batch_carrier_assignment` case was extended (this closure) to surface `BatchCarrierAssignmentScanContext`'s own carrier code and current location as additional printed lines, so this reused route shows a genuinely useful current-stage snapshot rather than only "Placement" + crop/variety. Reprinting an operational/lot label (which `batch_carrier_assignment` is) still requires a non-blank reprint reason on every call after the first, per PILOT-SCAN-001's own unchanged reprint-reason rule.

"Reprint Current Label" entry points were added, where a genuinely current-context listing screen already exists and already carries the placement's `batch_carrier_assignment_id`, to: the Germination worklist (covers Germination- and Seedling-eligible trays in one table), the Seedling workspace (`nursery/seedling/page.tsx`), and Leafy Production's "Active Production Plates" table. **No dedicated "currently in InterSalads" listing screen exists yet** (InterSalads' own page is transaction-composition only, with no current-occupancy table), so no entry point was added there — a genuine "where feasible" gap, not an oversight; adding one would require building a new listing screen, which this restrained closure ticket does not do. Vines Production/InterVines were left unchanged (their own placements tables could grow an equivalent link later, but were not required to close this ticket's three issues).

## Wiring scan context into operations (PILOT-SCAN-001E)

**Scan ≠ operation, restated for the wired-up flow:** every prepared `ScanAction.href` only ever navigates the operator to an existing, independent operational page. Landing on that page — even with context preselected — never itself records Harvest, Movement, Observation, Grading, Packing, Dispatch, a Quality release, or a Work Item completion. Each destination page still requires its own separate, deliberate submit; nothing about arriving there via a scan changes that page's own validation, authorization, or command execution. Opening `/scan` or `/q/[token]` never performs a mutation.

**Action link parameters now match what each destination page actually reads** (previously several had drifted, e.g. `crop_batch_id` sent where a page read `batchId`): Observation and Leafy Harvest read `batchId` (and, for Harvest, optionally the narrower `assignmentId` below); Grading reads `harvestLotId`; Packing reads `gradedLotIds`; Dispatch reads `finishedGoodsLotId`; Locations reads `highlight`. `qr_service.py`'s generated hrefs are the side that was fixed — no destination page's own query-param contract was renamed to match a link instead.

**Placement scan → exact placement context, never broad Batch fallback.** A `batch_carrier_assignment` QR identifies one specific physical placement of a Batch (see "Batch vs. placement" above) — it is not interchangeable with the parent Batch's own QR. Its `Harvest` action link therefore carries `assignmentId=<batch_carrier_assignment_id>` (in addition to `batchId`, for pages that also accept the wider context), and the Leafy Harvest page treats `assignmentId`, when present, as strictly narrower and authoritative over `batchId`: it resolves that exact id against the current authoritative harvestable-source read (the same `useHarvestablePlates` read the page already uses for manual selection) and selects only the one matching physical source. If Batch A exists in both GH1 and GH2, scanning the GH1 placement can never result in the GH2 portion being selected, shown as selected, or harvested.

If the scanned assignment is not found in that authoritative read — because it was released, already harvested, belongs to a different farm/tenant, or the id itself is invalid — the page does **not** fall back to selecting the whole Batch, does **not** guess or infer a different placement, and does **not** silently proceed with no selection. It shows an explicit stale/ineligible-context message and lets the operator return to Today on the Farm or re-scan. This is deliberately a dead end on stale context, not a degraded-but-functional one — a degraded fallback here is exactly the ambiguity a placement QR exists to prevent. The existing `workItemId` prefill and lost-response/duplicate-Harvest protections are unaffected by this: `assignmentId` only narrows *which physical source* is preselected, never which Work Item or which duplicate-submission guard applies.

**Location scan → View occupants lands on the scanned Location.** The Locations page reads a `highlight` query param and asks `LocationTree` to auto-expand every ancestor of that node and visibly mark it (ring highlight + scroll into view) with no manual expand-clicks — the same tree/read model the page already used, not a new location-detail view.

**Reprint-reason UX reflects the backend's real policy, not this browser session's own history.** The label preview (`LabelPreviewClient.tsx`) labels the reason field "(optional)" only for the three permanent entity types (Carrier, Asset, Location) — `record_label_print`'s own `_PERMANENT_ENTITY_TYPES` check, unchanged. For every other (operational/lot) entity type it always says "(required)" and blocks a blank submission client-side on every print request, never only once this session has itself already observed a prior print for that identity: neither `ScanContext` nor `QrIdentifierRead` exposes "has this ever been printed" on a plain read, so there is no truthful way for the frontend to know in advance whether the very next request is a genuine first print or a reprint of a label printed in an earlier session. Requiring a reason unconditionally for these entity types can never contradict the backend, which accepts a non-blank reason on a genuine first print exactly as readily as a blank one.

**Manual scan entry (`/scan`) is a fallback, never a second resolver.** It accepts a raw QR token or a full scan URL, extracts a bare token client-side (`lib/scan/normalizeScanInput.ts`), and always navigates to this app's own `/q/<token>` — the one existing authoritative resolver. The normalizer never returns a URL, only a token-or-error, so pasted input can never cause navigation to an external origin regardless of what host it names. FINAL CLOSURE: a full scan URL is additionally only accepted when its *origin* also belongs to an explicit allowlist (`ScanEntryPage` passes `[window.location.origin, GROWCMP_PRODUCTION_ORIGIN]`) — the current application origin (accurate in every environment without hardcoding any of them) plus the one fixed `https://growcmp.com` production origin every printed label's QR is built against. An absolute URL on any other origin is rejected outright even when its path is exactly `/q/<token>` (e.g. `https://evil.example/q/<realtoken>`) — path shape alone was never sufficient to call something a genuine GrowCMP scan link. No entity is resolved on `/scan` itself.

## Location-first scan validation (PILOT-SCAN-001F)

**Location-first validation is temporary operator context, not a farm record.** The "working location" an operator establishes by scanning a Location and tapping *Use as working location* is stored only in that browser's own `localStorage` (`lib/scan/workingLocation.ts`), never written to the backend, never a `FarmWorkItem`, never an occupancy/movement row, and never read by any domain command. It represents nothing more than "the operator says I am currently working here" — a client-side convenience the operator can Clear at any time, and which expires on its own after 12 hours (`WORKING_LOCATION_TTL_MS`) so a stale session can never silently keep validating against a location the operator left hours ago. **SCAN CONTEXT != FARM TRANSACTION** still holds completely: establishing, comparing, or clearing a working location never moves a Batch or Carrier, never changes occupancy or an Asset's location, never Harvests/records an Observation/Grades/Packs/Dispatches/completes a Work Item, and never "corrects" a mismatch it finds. It is a read-only comparison of two already-authoritative facts, nothing more.

**Comparison is by stable Location id, never by display path/code.** `LocationPathSummary` (the schema every current-location field on a `ScanContext` already used) gained one small additive field, `ids: list[uuid.UUID]` — the same root-to-leaf ancestor chain `codes` already described, but as the actual Location ids (`qr_service._location_path_summary`/`_resolved_location_summary`, sourced from `location_service.get_path`/`movement_service.get_resolved_location`'s own already-existing `id` columns — no new hierarchy logic, no migration). `lib/scan/validateScanAgainstWorkingLocation.ts`'s pure `validateScanAgainstWorkingLocation` function compares only `ids`, never `path_string`/`codes` (CLAUDE.md rule 3: locations are UUID-based, never string-matched).

**Result families**, returned as one discriminated `LocationValidationResult`:

- **MATCH_EXACT** — the scanned resource's current Location id equals the working location's id ("At selected working location").
- **MATCH_DESCENDANT** — the working location is a strict ancestor of the scanned resource's current Location ("Within selected working location"). Working parent + resource at a descendant is a valid match; the reverse (working location deep, resource's own recorded location coarser/an ancestor of it) is never automatically treated as a match — a coarser recorded location is never proof of exact placement at a narrower working location, so this case is a MISMATCH instead.
- **MISMATCH** — the scanned resource's current Location is neither the working location nor a descendant of it, or its farm differs from the working location's own farm (`reason: "different_farm" | "different_location"`). Never presented as a location-validated scan; withholds the scan's own physical-operation action links (see below) until the operator clears/replaces the working location or scans the correct item. Never triggers an automatic Move/Correction.
- **CANNOT_VALIDATE** — the scanned entity does not expose one authoritative current physical location. **A Crop Batch scan always falls here, unconditionally** — a Batch may occupy several Carriers/Locations at once, so a Batch-level QR is never sufficient proof of one specific physical portion's location, even when it happens to have exactly one active placement right now; the operator is told to scan the Placement or Carrier label instead. Harvested/Graded/Finished-Goods lot scans fall here too (no physical location is modeled for them yet — deliberately not added in this ticket). Every existing action link remains exactly as the backend sent it: this state never withholds anything, since the destination page's own domain validation still applies independently.
- **HISTORICAL** — a released `batch_carrier_assignment` (Placement). Checked before any location comparison, so a released placement whose former location happens to equal the working location is never shown as a green MATCH; its historical location may still be displayed for reference, never as current-location proof. (The backend already omits this entity type's own Harvest action once released, so no additional frontend filtering is needed for it.)
- **NO_WORKING_LOCATION** — nothing to compare against; renders no banner at all.

**Carrier reuse validates against the CURRENT occupant, never a historical one, by construction.** A Carrier's `current_location` (`CarrierScanContext.current_location`) is already resolved fresh from the Carrier's own current active occupancy (`movement_service.get_resolved_location`), independent of which Batch previously occupied it — unchanged since PILOT-SCAN-001. Reusing this same field for location-first validation means a Carrier reused from Batch A (released) to Batch B (current) validates against Batch B's location automatically, with no special-casing.

**Establishing a working location is always a deliberate click, never automatic.** Scanning a Location QR shows normal Location scan context plus a compact `WorkingLocationEstablishPanel`: *Use as working location* when none is active; when one already is, both the current and newly-scanned location are shown side by side with an explicit *Use `<code>` instead* button — an already-active working location is never silently replaced merely because another Location QR was opened. Scanning a second Location also runs the same generic comparison above (same Location → MATCH_EXACT; a child/descendant Location → MATCH_DESCENDANT; a sibling or unrelated branch → MISMATCH) — the establish action is independent of that comparison result and always available.

**Where it is shown:** a compact `WorkingLocationBar` (path + Clear + a link back into `/scan`) appears on `/q/[token]` (with the validation banner and any withheld actions), on `/scan` (display only — no comparison logic is duplicated there; the destination `/q/[token]` page performs the one, only comparison), and as a small non-dominant indicator on Today on the Farm. None of these add a dashboard.

**Action withholding is a client-side operator-context safety layer, never backend authorization.** `filterActionsForLocationValidation` withholds only the scan's own known physical-operation action labels (`Record Observation`, `Harvest`, `Grade this lot`, `Pack`, `Dispatch`, `Cold Storage`) when the result is MISMATCH; every read-only/navigation action (`View Batch`, `View traceability`, `View occupants`, `View current occupancy`) always remains. This changes no backend command validation or authorization — a destination page a MISMATCH did not withhold an action for (or that the operator reaches some other way) still performs its own full, unchanged domain validation.

## Work Item cross-reference

`farm_work_item_service.list_work_items_for_context` (additive) maps a scanned entity onto `FarmWorkItem`'s own structured context columns (PILOT-OPS-001) — never inferring a relationship those columns don't already express. Scanning does not start/complete a Work Item; opening one still follows PILOT-OPS-001's own rules (Work Item → real operation → authoritative result → completion/link).
