# Occupancy and Movement Model

Full detail: `CMP_MASTER_SPEC.md` §5–§6; `CLAUDE.md` rules 5–6, 10. This document summarizes the approved semantics; it does not restate the spec.

## Occupancy

A batch may occupy several carriers and locations at once. The system maintains **active occupancy plus history** — it never relies only on a single `current_location_id` field (`CLAUDE.md` rule 5). Occupancy supports exclusive positions, quantity capacity, partial occupancy, effective and recorded timestamps, and availability/history queries (spec §5).

## Movement vs transformation

- **Movement**: the same entity changes location. Identity is preserved.
- **Transformation**: inputs are converted into outputs (see `AUDIT_MODEL.md` for reconciliation rules).

These are distinct command types (`CLAUDE.md` rule 6) and must not be conflated in the API — movement is never expressed as a generic `PATCH` (`CLAUDE.md` "API and Offline Rules").

## Movement command validation

Before commit, a movement command validates: tenant and farm access; active source occupancy; allowed destination type/status; capacity and sanitation/release; workflow permission and approval; and duplicate/idempotent submission (spec §6). The movement, occupancy changes, and audit event commit atomically. Corrections use reversal plus a corrected movement — never a rewrite of history (`AUDIT_MODEL.md`).

## Idempotency

Every command (including movement) carries a client-generated UUID idempotency key. The server enforces uniqueness **per tenant and per command type** — a duplicate submission of the same key for the same tenant/command type is rejected or returns the original result rather than re-executing (`docs/adr/007-client-generated-idempotency.md`). Offline UI states are `queued`, `synchronized`, `rejected`, `needs attention`; queued work is never shown as server-confirmed.

## Occupancy and movement engine (implemented, CMP-006)

**Occupant and target.** An occupancy row refers to exactly one occupant (an asset **or** a carrier, never both) and exactly one target (a fixed location **or** an asset-relative position, never both), enforced by CHECK constraints. `assets`/`carriers`/`locations` carry no `current_location_id` — occupancy is the only source of placement, current and historical.

**Exclusivity (occupant side).** Two partial unique indexes (`WHERE end_time IS NULL`) enforce one active occupancy per asset and one per carrier — an occupant is never simultaneously present at two targets. This is the authoritative race-condition backstop, not the application layer.

**Capacity (target side, DOMAIN-FARM-002).** `locations.capacity` and `asset_positions.capacity` are nullable positive-integer columns: `NULL` or `1` means an effective capacity of 1 (exclusive — the original, backward-compatible behavior); `>1` permits that many simultaneous identified occupants. `capacity` is distinct from `occupiable` — a location may remain `occupiable = false` regardless of its configured capacity, and capacity alone never makes a target occupiable. This counts identified occupants (Carrier/Asset-occupancy rows), never a biological quantity (plants, seeds, kg, heads) — those remain out of this model. The universal target-side unique indexes (`ux_occupancies_active_target_location`, `ux_occupancies_active_target_position`) were removed and replaced by row-locking, concurrency-safe capacity enforcement inside `enforce_occupancy_insert_integrity`: the trigger locks the target row (`SELECT ... FOR UPDATE`) before counting active occupancies against `COALESCE(capacity, 1)`, so the authoritative backstop holds even for direct-SQL/ORM writes that bypass `movement_service`. The service layer performs the identical check under the same lock for a clean pre-commit error. Carrier-as-occupancy-target (a Grow Bag containing several Grow Cube carriers, `target_carrier_id`) remains out of scope — the target shape stays Location XOR AssetPosition only.

**Capacity reduction (DOMAIN-FARM-002.1).** A capacity *change* is enforced too, not only capacity at occupancy-insert time: `locations`/`asset_positions` each carry a `BEFORE UPDATE ... WHEN (NEW.capacity IS DISTINCT FROM OLD.capacity)` trigger that rejects any update where `active occupancy count > COALESCE(NEW.capacity, 1)` — a target already holding 3 active occupants cannot have its capacity lowered to 2, 1, or NULL while they remain active. No explicit lock is needed inside this trigger: a plain UPDATE already holds a row lock on the row it modifies before any BEFORE-trigger runs, and `enforce_occupancy_insert_integrity` locks that same row (`FOR UPDATE`) before counting — both paths therefore always serialize on the identical target row regardless of which started first, making the invalid combination (capacity below the committed active count) unreachable. Reducing capacity to a value that still fits, or increasing it, remains unrestricted. Occupancy rows themselves stay historically immutable beyond their one legitimate transition — see below.

**Occupancy update/lifecycle semantics (unchanged, reconfirmed by DOMAIN-FARM-002.1).** An `occupancies` row is inserted active-only and may be updated **exactly once**, to close it (`end_time`/`closed_by_movement_id` together, NULL → non-NULL) — enforced by the pre-existing `enforce_occupancy_closure_only` trigger (CMP-006, unmodified by DOMAIN-FARM-002/.1). Every other field, and any update once already closed, is rejected: an ended occupancy can never reopen, and an active occupancy's target or occupant can never be retargeted/reassigned in place — a real relocation is always a new occupancy row via a new movement, never an UPDATE. Because UPDATE can only ever *close* a row (never open or retarget one), it can never increase a target's active occupancy count — only INSERT does that, and INSERT is exactly what the capacity trigger above guards.

**Multi-occupant target reads (DOMAIN-FARM-002.1).** `GET .../locations/{id}/occupant` and `GET .../assets/{id}/positions/{id}/occupant` are legacy singular reads: for a capacity>1 target with several active occupants they report only one (the earliest by `effective_time`), but now carry an additive `active_occupancy_count` so that value is never silently presented as complete. The truthful, complete read is the new `GET .../occupant**s**` counterpart (`TargetOccupantsRead.active_occupancies`, deterministically ordered), and `operational_read_service.get_location_subtree_occupancy`'s `OccupiedLocation` gained an additive `occupants: list[LocationOccupant]` (complete) alongside the legacy `occupant` field (kept as `occupants[0]` for backward compatibility). Resolving the current target of **one specific** Carrier/Asset (`get_resolved_location`, `get_occupancy`) remains, correctly, singular and unchanged — occupant-side exclusivity was never in question; only target→occupants became plural.

**Compatibility.** A global, seeded `occupancy_compatibility_rules` table (same style as `location_type_hierarchy_rules`, but with no classification scoping of its own — a single global table) lists which occupant type may occupy which target type/position-kind — e.g. `germination_trolley → germination_chamber`, `seed_tray → shelf`, `seed_tray → slot`, `grow_bag → grow_bag_position`. Four partial unique indexes cover each occupant-kind × target-kind shape. Enforced in the service layer and, as a backstop, by a PostgreSQL trigger on `occupancies` insert. **Note (PILOT-UX-001B tripwire):** `target_position_kind` carries no AssetType scoping — a rule matches every `AssetPosition` of that `position_kind` regardless of which Asset owns it; see `ASSET_CARRIER_MODEL.md`'s own tripwire note for the full reasoning and the condition under which this must be revisited.

**Germination Trolley/Seed Tray placement (NURSERY-OPS-002A / PILOT-UX-001B).** A Germination Trolley Asset occupies a Germination Chamber Location directly (`germination_trolley → germination_chamber`, replacing the retired `germination_trolley → chamber_position` rule — see `LOCATION_MODEL.md`). A Seed Tray Carrier occupies a Trolley's Level `AssetPosition` directly (`seed_tray → shelf`, PILOT-UX-001B, `direct_level`) or one of that Level's legacy child Slot `AssetPosition`s (`seed_tray → slot`, unchanged, `legacy_level`) — classified per Level, never per Trolley (a single Trolley may carry both kinds). A `legacy_level`'s own row is never itself a valid target (the caller must target one of its child Slots); an `invalid_level` (no child Slots, no configured capacity) is rejected as a configuration error, never silently treated as capacity=1. Direct Seed-Tray-to-Chamber placement is deliberately **not** a compatible pair (out of scope; a Tray must always go through a Trolley Level or Slot). Both Trolley and Tray placements reuse the generic Movement/Occupancy engine above verbatim via `germination_service.py`'s thin orchestration layer — no second physical-movement engine — which additionally enforces the Germination-specific business rules the generic engine cannot express: per-Level legacy/direct/invalid classification, and that a Seed Tray may only be placed while that Trolley *currently* occupies a valid Nursery Germination Chamber (checked fresh against live Occupancy on every call, never cached); attempting to place a Tray onto a Trolley that is not currently in Germination is rejected even though the generic Movement primitive would otherwise permit it. Moving an already-placed Trolley from one Chamber to another closes and reopens only the Trolley's own Occupancy row — every Seed Tray resting on its Levels/Slots keeps its own Occupancy (and `BatchCarrierAssignment`) completely unchanged; their *resolved* location changes automatically because resolution walks through the Trolley's current Occupancy at read time (see **Derived location** below), not because anything about the Tray was rewritten. Physical placement carries no biological Germination outcome (that remains a separate, later concern — `GerminationCheck`/germination percentages/loss reconciliation are untouched by this model).

**Generic movement bypass closed for Germination (PILOT-UX-001B).** The fully generic `POST /farms/{farm_id}/movements` route rejects any attempt to move a `seed_tray` Carrier onto an AssetPosition owned by a `germination_trolley` Asset (Level or legacy Slot) — a Seed Tray must always reach a Germination Trolley position through `germination_service.place_tray`, which alone carries the sown-state and Trolley-currently-in-Chamber validation the generic endpoint cannot express. The guard (`germination_service.reject_generic_bypass_for_seed_tray_placement`) is called only from `api/movements.py`, the generic route's own HTTP boundary — `movement_service.execute_movement` itself remains fully generic and untouched, and `place_tray`'s own direct call into it is unaffected.

**Seedling Table placement (NURSERY-OPS-003A).** A Seed Tray Carrier occupies a Seedling Table Location directly (`seed_tray → seedling_table`) — the authoritative Nursery Seedling topology stops at the Table itself (no `seedling_table_position`, matching the `cultivation_plate → grow_table` direct-occupancy precedent, `LOCATION_MODEL.md`). Seedling Table capacity means the number of simultaneous physical Seed Tray occupants, exactly the same generic capacity mechanism as everywhere else in this model — never a seedling/plant count. Table-to-Table movement during the active Seedling stage is technically permitted by the generic engine (no frozen prohibition exists) but has no dedicated operator workflow yet — a deferred product-policy question, not a code gap. `movement_service` itself gained **no** Germination/Seedling awareness from this ticket: every Seedling-specific rule (a completed Germination handoff must exist before a *biological* Seedling entry can be recorded) lives entirely in `seedling_entry_service.py`'s own orchestration layer, exactly as `germination_service.py` already keeps Germination-specific rules out of the generic engine.

**InterSalads Table placement (NURSERY-OPS-004B.1).** A Nursery Cultivation Plate Carrier occupies an InterSalads Table Location directly (`nursery_cultivation_plate → intersalads_table`, migration `b7e2f4a9c1d6`) — the topology stops at the Table, matching the `seed_tray → seedling_table`/`cultivation_plate → grow_table` direct-occupancy precedent; no `intersalads_table_position` exists. InterSalads Table capacity means the number of simultaneous physical Plate occupants — the same generic mechanism as everywhere else in this model, and a distinct concept from `CarrierSpecification.biological_position_count` (the number of plants one Plate can hold; `docs/domain/TRANSPLANTATION_MODEL.md`'s own NURSERY-OPS-004B.1 addendum). `movement_service` gained no Transplant/InterSalads awareness from this ticket: `intersalads_transplant_service.py` composes the existing `_execute_movement_core` with `transplant_service._record_transplant_core` under one caller-owned transaction — the first real production composition of the two — exactly the same "generic core stays biology-blind, orchestration owns the domain-specific rule" discipline this Germination/Seedling placement work already established.

**Movement core/wrapper split (NURSERY-OPS-003A).** `movement_service.execute_movement` is now a thin wrapper around `_execute_movement_core` (validate + lock + insert + flush, no commit) plus its own trailing `db.commit()`/`db.refresh()` — every existing caller's behavior is unchanged (proven by the full pre-existing Movement/Occupancy test suite staying green). The split exists so `seedling_entry_service.record_seedling_entry` can perform the physical Movement and insert its own immutable biological-handoff-anchor row (`OBSERVATION_QUALITY_MODEL.md`'s NURSERY-OPS-003A addendum) inside **one** transaction/commit — either both survive or neither does — reusing the exact extraction pattern `location_service._create_location_core` already established for FARM-SETUP-001's own multi-row atomic commands.

**Movement command.** `POST /farms/{farm_id}/movements` is the only write path — there is no direct occupancy-insertion endpoint. One command covers placement (no prior occupancy), a normal move (closes the old occupancy, opens a new one), and removal (closes only, no destination); the source is always server-derived from the occupant's current active occupancy and is never accepted from the client. Movements are immutable (insert-only, enforced by trigger) and carry a client-generated `client_command_id`; uniqueness is enforced per `(tenant_id, command_type, client_command_id)`. A retried command with an identical payload returns the original movement; the same id with a different payload is rejected. Concurrent duplicate submissions are resolved the same way once serialized by the occupant row lock.

**Closing an occupancy** is the only update an occupancy row ever receives, and only transitions `end_time`/`closed_by_movement_id` together from NULL to populated — enforced by a trigger, since "which columns changed" and "was it already closed" both require comparing OLD and NEW, not expressible as a CHECK.

**Derived location.** Reading an occupant's resolved location never touches occupancy rows other than its own: an asset resolves directly through its fixed-location path; a carrier in an asset position resolves its relative position path, then separately looks up the *containing asset's own* active occupancy to continue into the fixed-location path — reporting an explicit unresolved reason if the containing asset isn't placed anywhere, rather than fabricating one. Moving the containing asset never touches the carrier's occupancy row.

**Deferred:** crop batches, transformations, QR/scan identity, maintenance, and location reparenting all remain out of scope. Multi-capacity targets are implemented (DOMAIN-FARM-002, above); Carrier-as-occupancy-target and biological-quantity tracking (plants/seeds/kg per occupant) remain deferred.

**Person custody is not a third target kind (frozen, STORE-INV-001 family).** A User/person is deliberately never added as a third occupant target alongside Location and AssetPosition — a person is not a physical Location. Human custody of an Asset (equipment checkout) is a separate future concept, `AssetCustodyAssignment` (`STORE-INV-005`), independent of and never a substitute for the Asset's real physical Occupancy. See `docs/domain/STORE_INVENTORY_MODEL.md` §13.
