# Observation, Germination Check, and Quality Hold Model

Full detail: `CMP_MASTER_SPEC.md` §2, §8; `CLAUDE.md` rules 1, 3, 5, 7, 10, 12. This document summarizes the approved model as implemented in CMP-010; it does not restate the spec.

## Two measurement shapes, on purpose

Independent, tenant-defined metrics (temperature, humidity, EC, pH, plant height, visual notes) go through the generic `observation_definitions` / `observation_events` / `observation_values` system: one typed value per definition per target, bounded only by that definition's own static min/max. Germination is different — its integrity rules (`germinated ≤ observed`, category counts within the inspected population) compare *sibling counts from the same inspection*, which a per-value CHECK on separate EAV rows cannot express. Rather than build a cross-row trigger keyed to specific definition codes (a rule engine CMP-010 deliberately avoids), germination gets its own narrow, immutable `germination_checks` table: one row per assignment per event, with real columns, so ordinary same-row `CHECK` constraints enforce every rule directly. Both shapes attach to the same `observation_event` and are included in one fingerprint and one audit event — an event may carry generic values, germination checks, or both.

## Observations never rewrite sowing quantities

`germination_checks.inspected_site_count` is validated against — never written into — the CMP-009 `sowing_event_lines.sown_site_count` for the same assignment (a trigger join, since the two tables are otherwise unrelated). `germination_percentage` is derived at read time from `(normal + abnormal) / inspected * 100` using `Decimal` arithmetic throughout the read path — it is never a stored column, so there is nothing to keep in sync.

## Targets and assignment timing

Each observation definition declares a `target_scope`: `crop_batch` (no assignment), `carrier_assignment` (assignment required), or `either`. A referenced assignment must belong to the same batch as the observation event but is **not** required to belong to the batch's *current* stage run — a carrier assigned during seeding can still be observed during germination. What is enforced is temporal: an observation's effective time can never precede the assignment's own `assigned_effective_time`. Assignment "active" here means CMP-009's existing `released_effective_time IS NULL` — CMP-010 adds no release mechanism of its own.

## Quality holds block progression, releases don't mutate them

A `quality_hold` is immutable and batch-level; multiple simultaneous open holds are permitted (the alternative — capping one open hold at a time — adds dedup complexity for no real benefit, since "any open hold blocks" already generalizes cleanly). Open vs. released is never a stored status: it is derived from whether a `quality_hold_releases` row exists for that hold, mirroring CMP-009's own release-by-absence convention on `batch_carrier_assignments`. A hold's optional `source_observation_event_id` must reference an observation on the same batch with an effective time no later than the hold's own.

## Stage-progression blocking is enforced twice

`crop_batch_service.transition_stage` (CMP-008) checks for an open hold immediately after its existing post-lock idempotency recheck and before any other validation — so an exact replay of an already-successful transition still returns its original result even if a hold was placed afterward, but any *genuinely new* transition attempt is rejected outright. As defense in depth against direct SQL or a future bypass of that service function, a trigger on the **existing** `batch_stage_transitions` table (`batch_stage_transitions_enforce_no_open_hold`) rejects any `INSERT ... command_kind = 'stage_transition'` row while an open hold exists for that batch — the trigger's `WHEN` clause means it never fires for `command_kind = 'initial_entry'`, so batch creation is untouched. Both checks share one locking discipline: hold placement, hold release, and stage transition all serialize on the same `crop_batches` row lock CMP-008 already established, so no new concurrency primitive was introduced.

## Database protection

Composite foreign keys prove tenant/farm/batch consistency structurally, reusing CMP-008/009's existing `(tenant_id, farm_id, ...)` composite constraints wherever they already covered what CMP-010 needed — no additive constraint was required on any pre-existing table (verified against the live schema before writing the migration). Triggers are reserved for genuinely cross-row rules: an observation value's typed column matching its definition's `value_type` and numeric/percentage bounds (requires reading `observation_definitions`), a germination check's `inspected_site_count` against the sown count (requires reading `sowing_event_lines`), and the two stage-progression trigger described above. Observation-definition rows are immutable except `status` — a dedicated trigger permits only that one field (plus `updated_at`) to change, matching the same pattern CMP-007 established for workflow lifecycle fields.

## Hold-blocking scope across tickets

Quality holds are not a global lock — each later ticket that gates on them extends the net deliberately, not automatically: CMP-010 holds block stage progression (`transition_stage`, above). CMP-012 holds also block batch split/merge (identity derivation) — a genuinely new derivation command creating a real hold-blocked scenario, checked with the same replay-before-mutable-state discipline. CMP-013 holds also block harvested-produce-lot creation — reusing `quality_hold_service.has_open_quality_hold` at the service layer, plus (a first for this net) a DB-level `SELECT ... FOR UPDATE`-locked check inside the harvest-event insert-integrity trigger, so a direct-SQL insert genuinely serializes against hold placement rather than relying on an unlocked read. CMP-015 holds also block packing consumption — a genuinely new packing command is rejected while any *source produce lot's* crop batch carries an open hold, checked at the service layer after locking every source batch, plus independently inside the packing-input-line insert-integrity trigger (see `docs/domain/PACKING_MODEL.md`). CMP-011 transplantation remains **unaffected** — it is a same-stage transformation the hold net was never extended to, and this document's own scope does not implicitly widen to cover it.

## Deferred

Carrier release/reassignment, transplanting, transformations, automatic stage progression, automatic pass/fail rules, scoring/formula engines, approval workflows, role-specific hold authority, correction/void of observations or holds, seed inventory deduction, laboratory integrations, sensors/IoT ingestion, occupancy/movement changes, QR identities, labels, frontend, RLS.

CMP-020's recall containment (`docs/domain/RECALL_CONTAINMENT_MODEL.md`) is deliberately independent of this net, not an extension of it: a recall case never auto-creates a quality hold, closing a recall never releases a hold, and releasing a hold never closes a recall. Recall containment blocks storage release and dispatch — two operations this document's own hold net never reached — as an additional, separately-checked gate.

Split/merge (CMP-012), harvest (CMP-013), and packing (CMP-015) are implemented — see `docs/domain/BATCH_DERIVATION_MODEL.md`, `docs/domain/HARVEST_MODEL.md`, and `docs/domain/PACKING_MODEL.md`; all three extend the hold-blocking net described above without altering the stage-progression behavior documented here.

## NURSERY-OPS-002B addendum: two Germination models that never redefine each other

**LEGACY site-based observation (`germination_checks`, unchanged in meaning).** Site/cell-based; `inspected_site_count`/`normal_germinated_site_count`/`abnormal_germinated_site_count`/`failed_site_count` count physical tray sites, not individual seedlings. Requires a genuinely-recorded `SowingEventLine.sown_site_count` for the assignment — this was always true, but a real pre-existing defect meant "no sowing line row at all" and "a row exists with `sown_site_count` still NULL" (the shape every NURSERY-OPS-001 operator-sown Tray has) produced the exact same misleading exception. Corrected via `CREATE OR REPLACE FUNCTION` on `enforce_germination_check_insert_integrity` (migration `7bddca3261cc`, the historical migration that created the function is untouched) to raise a distinct, accurate message for the second case. This does **not** make legacy site checks writable for modern-sown Trays — it only tells the truth about *why* they still cannot be, since `sown_site_count` genuinely was never recorded for them. `germination_percentage` remains `(normal + abnormal) / inspected_site_count * 100` — sites, never seeds.

**MODERN, INDIVIDUAL-SEEDLING-based outcome (`germination_outcome_snapshots`, new).** A separate, dedicated table — reuses the existing `observation_events` immutable header verbatim (same tenant/farm/batch scope, actor, effective_time, `client_command_id`/`request_fingerprint` idempotency, audit) via `germination_outcome_service.py`, a thin orchestration layer, not a second event framework. One row per (event, assignment); an assignment may accumulate many rows across many events over time. Exact semantics:
- **Denominator/input**: `SowingEventLine.seed_count` — never `sown_site_count`. Frozen product decision: Imperial operators count individual emerged seedlings/plants, not tray cells.
- **`normal_seedling_count` + `abnormal_seedling_count` = `living_seedling_count`** — both are LIVING; abnormal/weak seedlings are explicitly **not** a loss, rejection, or mortality here. If an abnormal seedling is later physically removed, that is a separate future operation's fact, not this one's.
- **The gap** (`seed_count - living_seedling_count`) is recorded implicitly (derivable, never stored) and is deliberately **never** categorized — no `NON_GERMINATION` or other loss reason is inferred; the missing quantity could represent several different biological realities this ticket does not attempt to distinguish.
- **Snapshots are point-in-time, never additive.** Repeated rows for one assignment each describe what was observed at that `effective_time`; later counts do not sum with earlier ones, and a later count may legitimately be lower than an earlier one (correction, reclassification, or genuine loss between observations).
- **`assessment_complete`** (per snapshot, per assignment — never per-Batch) distinguishes a provisional observation from the snapshot the operator declares as establishing the Tray's authoritative downstream handoff quantity. "Complete" does not mean every seed is categorized — only that the operator considers this snapshot final for handoff purposes.
- **Current vs. authoritative**: "current observed state" = the latest snapshot by `(effective_time, recorded_time)`; "authoritative Germination handoff" = the *latest completed* snapshot's `living_seedling_count`, or unresolved/unavailable if no completed snapshot exists yet. Never substitute `seed_count` or a provisional snapshot for the authoritative figure.
- **No-reopening invariant, enforced symmetrically.** Once an assignment has a completed snapshot at effective time T, a new snapshot with `assessment_complete=false` and `effective_time > T` is rejected (would ambiguously reopen an established handoff); symmetrically, a new *completed* snapshot is rejected if a provisional snapshot with a later `effective_time` already exists for that assignment. The second direction exists specifically so the invariant holds even when two commands race concurrently and are serialized (via the same `CropBatch` row lock `record_observation` already takes) in an order that disagrees with their own `effective_time` values — enforced identically in the DB trigger (`enforce_germination_outcome_snapshot_insert_integrity`) and in `observation_service.record_observation`'s own validation, not only one or the other. Historical backfill (a provisional dated at or before the latest completion) remains allowed; multiple completed snapshots over time remain allowed, with the latest always authoritative.
- **Temporal assignment validity, not current-state validity.** Unlike the legacy `values`/`germination_checks` validation (left unchanged — still `released_effective_time IS NULL`), a modern outcome's write-time check is `assigned_effective_time <= effective_time < released_effective_time` (or unreleased) — a late/historical entry for a Tray that has *since* been released remains valid if the observation's own effective time predates the release.
- **No side effects.** Recording an outcome never touches `BatchCarrierAssignment`, `Occupancy`, `Movement`, creates no Transplant/Batch-derivation event, and never auto-transitions workflow stage. Physical placement (NURSERY-OPS-002A) and biological outcome are, and remain, separate facts — the UI defaults toward Trays currently `IN_GERMINATION` but never hard-blocks on it.
- **No shared loss catalog.** `NON_GERMINATION`/`WEAK_SEEDLING`/`MORTALITY`/etc. are explicitly out of scope; no other CMP stage (harvest, packing, transplant) uses that catalog today either, so introducing it here first would be a premature, unused abstraction.

Historical `germination_checks` rows (if any exist) are read exactly as recorded — the migration never rewrites, reinterprets, converts, or backfills them into the modern shape; the modern outcome model starts prospectively only. See `SEED_SOWING_MODEL.md`'s own NURSERY-OPS-002B addendum for the Seeds-vs-Sites boundary this model depends on.

## NURSERY-OPS-003A addendum: the Seedling Entry biological handoff freeze

A completed Germination outcome cannot remain a *dynamically re-resolved* fact forever: once a Tray genuinely enters Seedling operations, CMP must record — permanently — exactly which completed `germination_outcome_snapshots` row supplied the starting biological quantity. Otherwise a later, even historically truthful, Germination reassessment (section above — multiple completed snapshots over time remain legal) could silently change a quantity Seedling operations has already built history on top of.

**`seedling_entries` (new, immutable, insert-only).** One row per `BatchCarrierAssignment`, ever (`ux_seedling_entries_assignment`) — a later physical Movement (e.g. a future Table-to-Table move) is not another biological entry. References `source_germination_outcome_snapshot_id` and freezes `starting_living_seedling_count = source.normal_seedling_count + source.abnormal_seedling_count` at the moment of entry — both server-resolved and server-derived, never caller-supplied, and DB-verified equal to the referenced snapshot's own counts at INSERT time (`enforce_seedling_entry_insert_integrity`). Abnormal seedlings remain counted as living here too, exactly as in the snapshot itself — the freeze changes *when* the quantity is fixed, never *what* it means.

**Historical resolution, not "latest completed now".** Given the entry's own `effective_time` T, the frozen source is the latest **completed** snapshot for that assignment whose own `effective_time <= T` (`seedling_entry_service._resolve_source_snapshot`) — the same historical-truth principle NURSERY-OPS-002B.1 established for `ObservationEvent`'s own stage-run resolution, applied here to snapshot resolution instead. A provisional snapshot, `SowingEventLine.seed_count`, or `sown_site_count` can never substitute for a genuine completed handoff (`NoCompletedGerminationHandoffError`).

**A later Germination correction never rewrites an already-frozen entry.** Once `starting_living_seedling_count` is frozen, it stays frozen — a subsequent completed snapshot (however historically valid on the Germination side) is simply a new fact the Germination-side reads reflect; it never cascades into an existing `SeedlingEntry` row, by construction (the row is immutable, and nothing re-reads "latest completed" after freezing). Any resulting discrepancy between the frozen anchor and a later Germination-side correction remains visible for manual reconciliation — never silently absorbed (`CLAUDE.md` rule 8).

**One atomic command, two separate facts.** `seedling_entry_service.record_seedling_entry` commits a physical `Movement` (Trolley Slot → Seedling Table, via `movement_service`'s own unmodified engine, see `OCCUPANCY_MOVEMENT_MODEL.md`) and this immutable anchor row in ONE transaction — either both survive or neither does. The DB trigger additionally verifies the referenced Movement's own tenant/farm/occupant/destination-type/effective_time consistency (the Movement's destination must resolve to a `seedling_table` location, and its `effective_time` must exactly match the entry's own — one operator command, one handoff time, never two independently-supplied clocks). `movement_service` itself remains completely unaware of any of this — see `OCCUPANCY_MOVEMENT_MODEL.md`'s own NURSERY-OPS-003A addendum.

**No Seedling biological loss/removal yet.** Until a later, separate ticket, current biological quantity for a Tray with a `SeedlingEntry` is simply its own `starting_living_seedling_count`, unconditionally — no loss event, no category catalog, no current-quantity ledger exists yet. A Tray may physically occupy a Seedling Table with no `SeedlingEntry` at all (derived state `in_seedling_unanchored`, never conflated with a genuine biological entry) since generic Movement remains unconditional on biological readiness by design (`OCCUPANCY_MOVEMENT_MODEL.md`).

## NURSERY-OPS-003B addendum: Seedling biological dispositions and current living quantity

NURSERY-OPS-003A froze the *starting* Seedling quantity; NURSERY-OPS-003B adds the immutable, insert-only ledger of biological quantity changes that happen *after* that freeze — confirmed mortality, weak/diseased/pest/physically-damaged seedlings, QC rejections that stop continuing, and samples pulled. Deliberately named "disposition," never "loss" — a QC rejection or a sample is not a loss in the agronomic sense, and the term must cover all eight approved reasons without implying one.

**`SeedlingDispositionReason` (new, global, 8 rows, no tenant scope, no write API).** `WEAK_SEEDLING`, `DISEASE`, `PEST_DAMAGE`, `PHYSICAL_DAMAGE`, `MORTALITY`, `QC_REJECTION`, `SAMPLE`, `OTHER` — seeded once by the migration and never editable at runtime, mirroring `LocationType`/`CarrierType`'s reference-table precedent except `code` is itself the primary key (no separate UUID), a deliberate deviation that lets the OTHER-requires-note rule live as a same-row `CHECK` instead of a cross-table trigger. `NON_GERMINATION` and `TRANSPLANT_DAMAGE` are explicitly excluded — the first belongs to Germination's own gap concept, the second to a future transplant-boundary ticket, neither is a Seedling biological disposition.

**Confirmed mortality is immediate; physical cleanup is a separate, later fact.** A dead seedling stops counting as living the moment its disposition is recorded — biological population truth and physical carrier contents are distinct concepts (`CLAUDE.md` rule 6: movement vs. transformation), and this ledger only ever asserts the former. The operator always supplies the positive count of seedlings that stopped continuing, never a recount of the whole remaining population (Section 0.2) — the same "delta the operator observed, not a snapshot they reconstruct" discipline `MOVEMENT`/ledger commands elsewhere in CMP already follow.

**QC hold/observation alone never changes quantity.** `QUALITY_HOLD_MANAGE`/`OBSERVATION_ENTRY_MANAGE` remain entirely unaware of this ledger — a `QC_REJECTION` disposition becomes a quantity-reducing fact only when an operator explicitly records that those seedlings have stopped progressing in the continuing population, exactly like every other reason. This preserves the existing invariant (`Quality holds block progression, releases don't mutate them`, above) that a hold is a gate, never a mutation.

**`SeedlingDispositionCommand` + `SeedlingDispositionEvent` (new, header-plus-immutable-child-rows, same shape as `SowingEvent`+`SowingEventLine`).** A RECORD command creates exactly one REDUCTION event (a negative `quantity_delta`); a CORRECT command creates exactly one REVERSAL (the exact negation of its target, sharing the target's own `effective_time`) and, optionally, one replacement REDUCTION — one atomic transaction either way, never two separate commits. Deliberately not built on `ObservationEvent` — a disposition is a quantity-reducing ledger fact, not a descriptive observation, the same reasoning NURSERY-OPS-003A already applied when it gave `SeedlingEntry` its own dedicated header rather than reusing one.

**Current balance is always derived, never persisted.** `starting_living_seedling_count` (frozen by `SeedlingEntry`, never re-derived) plus `SUM(quantity_delta)` over that entry's disposition events — the same live-`SUM()` pattern `ProduceLotLedgerEntry`/`FinishedGoodsLedgerEntry` already established, chosen again here for the same reason: an insert-only signed-delta ledger can never drift from its own history because there is no separate running total to keep in sync. Enforced non-negative and never exceeding the starting count at every point in chronological order (grouped by `effective_time`, not insertion order, so two same-instant deltas can never be validity-ordered by accident) — both at the service layer (row-locked) and, as a backstop, inside the event-insert trigger.

**Correction is reversal, never rewrite.** Voiding a disposition creates only its exact reversal (no meaningless zero-quantity row); replacing it creates that same reversal plus a new, ordinary REDUCTION. The original erroneous event is never hidden, deleted, or edited — it stays visible in history with explicit linkage to whatever reversed or replaced it (`CLAUDE.md` rule 7). Correction chains stay flat: a REDUCTION may be reversed at most once, a REVERSAL can never itself be reversed, and a replacement REDUCTION is a normal immutable REDUCTION that may later be corrected exactly once in turn — no reversal-of-reversal, no circular chains, enforced by a partial unique index on `reverses_event_id` plus same-row kind checks.

**Movement- and transplant-independent, by design.** Recording or correcting a disposition never creates, reads, or is gated by `Occupancy`/`Movement`/`BatchCarrierAssignment` placement — a Tray's physical location is informational context only, never a hard requirement, exactly the posture NURSERY-OPS-002B's Germination outcome already established. `transplant_service` is unmodified by this ticket and does not validate against this ledger's balance — a real gap, deliberately left for the future Seedling→InterSalads/InterVines handoff ticket rather than invented here.

**Temporary integrity guard, explicitly provisional.** Until that future handoff exists to freeze its own downstream input quantity, a new disposition or correction is accepted only while the source `BatchCarrierAssignment` is still currently active — once released, no new backdated disposition and no new correction are accepted (though exact replay of an already-successful command still works, per the idempotency discipline every command in this codebase shares). This is deliberate temporary protection, not a permanent architectural constraint, and may be relaxed once the handoff ticket exists.

**Authorization.** A dedicated `BIOLOGICAL_DISPOSITION_MANAGE` permission, distinct from `OBSERVATION_ENTRY_MANAGE` — granted to `operator` and `production_supervisor` (the roles already trusted with `SOWING_MANAGE`/`TRANSPLANT_MANAGE` on the floor), and to `tenant_admin` automatically via the existing all-permissions convention. Reads reuse `SOWING_READ`, matching the read-permission precedent NURSERY-OPS-003A already set for the Seedling Tray list.

**Frontend.** A dedicated `/farms/{farmId}/nursery/seedling` page — current living quantity per Tray, a record-disposition form (configure → review, the backend always recomputes and returns the resulting balance; the client never trusts or displays a computed post-submit balance), and an un-collapsed disposition-history view per Tray offering "Correct" only on a still-uncorrected REDUCTION, matching the chain rule above. Deliberately not added to the Germination page, which owns physical placement and the Germination-outcome handoff only.

## NURSERY-OPS-004A addendum: the Seedling Source Checkpoint and transplant balance-window boundary

NURSERY-OPS-003B's own "temporary integrity guard" section (above) explicitly named the gap this ticket fills: `transplant_service` was unmodified by 003B and never validated against the disposition ledger's balance. 004A closes that gap — the authoritative *source* quantity for a transplant is now always server-derived from `SeedlingEntry` + `SeedlingDispositionEvent` + a new `SeedlingSourceCheckpoint`, never caller-supplied and never bounded by `sown_site_count`/`seed_count` (which is why a modern, NURSERY-OPS-001.1 Nursery Tray — whose `sown_site_count` is deliberately NULL — could never transplant at all before this ticket).

**`SeedlingSourceCheckpoint` (new, immutable, insert-only, one row per `TransplantSourceLine`).** Each checkpoint closes the currently-open biological balance window and opens a new one: `remainder_after` becomes the new anchor value, `effective_time` the new anchor time, for every `SeedlingDispositionEvent` recorded from that point forward against the same `seedling_entry_id`. Chained via `previous_checkpoint_id` to the actual latest prior checkpoint for the same Tray (or `NULL` for the first). Window membership is resolved purely temporally, against `effective_time` — deliberately no `checkpoint_id` column was added to `seedling_disposition_events`; a second insert-time pointer would duplicate what `effective_time` comparisons already prove and could drift from it.

**The anchor formula, identical in the service layer and the DB trigger.** `anchor_value = latest_checkpoint.remainder_after`, `anchor_time = latest_checkpoint.effective_time` if any checkpoint exists for the Tray, else `SeedlingEntry.starting_living_seedling_count` / `SeedlingEntry.effective_time`. `source_available(T) = anchor_value + SUM(disposition deltas WHERE anchor_time < effective_time <= T)`. Exposed publicly as `seedling_disposition_service.get_source_availability_anchor`/`get_source_available`, the one place both `transplant_service` and the disposition ledger agree on what "currently available to transplant" means.

**Strict checkpoint temporal floor, symmetric across both consumers of the ledger.** Once a checkpoint exists, both a new disposition and a new transplant must have `effective_time` strictly greater than that checkpoint's own `effective_time` — a checkpoint has already frozen everything through its own instant, so an event *at* that instant is rejected, not merely one before it (`SeedlingDispositionPredatesCheckpointError` on the disposition side; `InvalidTransplantEffectiveTimeError` on the transplant side, backstopped by the DB trigger either way). Before any checkpoint exists, the floor is at-or-after the `SeedlingEntry`'s own `effective_time` — equality is allowed there, since nothing has closed that window yet.

**Pre-checkpoint corrections are frozen.** `seedling_disposition_service.correct_disposition` now also rejects correcting (voiding or replacing) any disposition whose own `effective_time` is at or before the latest checkpoint — that fact has already been consumed into an immutable transplant handoff and can no longer be changed, the same "already-frozen, never rewritten" posture NURSERY-OPS-003A established for `SeedlingEntry` itself.

**Partial and sequential transplant of the same Tray.** `TransplantSourceLine`'s old lifetime-once `UNIQUE(source_batch_carrier_assignment_id)` is replaced with `UNIQUE(transplant_event_id, source_batch_carrier_assignment_id)` — the same source assignment may now appear across multiple, sequential transplant events, each producing its own source line and its own checkpoint, chained to the prior one. A source assignment is released **iff** its own checkpoint's `remainder_after = 0`; otherwise it stays active, eligible for a later, further partial transplant against the same, still-open balance window.

**Full reconciliation, per source and per event.** Each source line now separates its loss into four categorized, DB-summed fields — `transplant_damage_count`, `qc_rejection_count`, `sample_count`, `other_loss_count` (with a required note) — whose sum is DB-enforced equal to `discarded_plant_count`. Per source: `source_available_before = successful_transferred + discarded_plant_count + remainder_after`. Per event: `total_source_available_before = total_destination_plant_count + total_discarded_plant_count + total_remainder_after` (`CLAUDE.md` rule 8 — no hidden differences).

**Write order matters: checkpoint before release, not after.** A source assignment's conditional release is the *last* row-level write in `record_transplant`, strictly after its own checkpoint has already been inserted — the checkpoint insert-integrity trigger itself asserts the assignment is still active at checkpoint-insert time (defense against post-hoc checkpoint fabrication), so releasing first would make every full-consumption transplant trip that guard against itself.

**`current_living_seedling_count` vs. `current_source_available_count` — deliberately different questions.** The former (003B, unchanged) is checkpoint-unaware: `starting_living_seedling_count` net of every disposition ever recorded, regardless of any transplant. The latter (new) is the checkpoint-aware figure this ticket actually needs to answer "how many plants remain available to transplant right now." A fully-consumed Tray (`remainder_after = 0`, assignment released) can show `current_source_available_count = 0` while `current_living_seedling_count` is still positive — the two numbers answer genuinely different questions and must never be conflated. `SeedlingBiologicalTrayRead.is_depleted` was accordingly redefined around `current_source_available_count == 0`, not the living count.

**A pre-existing trigger taught about the new multi-line reality.** `enforce_batch_carrier_assignment_closure_only_v2` (originally CMP-012's `a4d92f7c1e6b`) validated a release by looking up "the" `transplant_source_line` for an assignment with an unordered, unfiltered `SELECT ... INTO` — safe only while the old lifetime-once uniqueness held. Updated via the same `CREATE OR REPLACE` pattern (original text preserved, only the function body changes) to filter directly on the releasing event, since an assignment can now legitimately have more than one source line across its history.

**Deferred.** InterSalads/InterVines carrier and location work (NURSERY-OPS-004B/004C), any new Nursery transplant operator UI, and any transplant correction/void mechanism are all explicitly out of scope here — a transplant, once recorded, cannot yet be corrected. 004A is a backend foundation only; Nursery transplant is not yet production-ready for floor operators until 004B/004C land.
